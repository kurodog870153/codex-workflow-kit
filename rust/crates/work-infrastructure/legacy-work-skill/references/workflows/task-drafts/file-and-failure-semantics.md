# File and failure semantics


1. The effective entry point is `outputs/work/tasks/<requirement-id>/drafts/index.json`. Each entry's `draft_ref` contains `save_revision`, draft `revision` and `sha256`; the historical path is `history/<save_revision>/<TASK-ID>.json`.
2. Every save exclusively reserves `history/<index-revision>/`, writes its index and changed draft, verifies bytes, and atomically switches the effective index. Unchanged drafts retain their earlier references. The root-level `<TASK-ID>.json` is a display copy only.
3. A successful save with `mirror_status: stale` is committed despite the outdated display copy. Report that condition and continue to use historical reads. `superseded` means a newer index was observed; read current progress before another write.
4. A nonzero exit is a stop. A stale revision requires reading and reviewing the new progress, not blindly retrying. `draft_save_interrupted` preserves the previous committed index and may leave a reserved history directory. After separate user authorization, recover a `draft-save-request` using `draft-recover-request` with the identical discussion JSON, original expected revision and all original source/selection arguments. It rechecks live sources and derives the original proposal from historical metadata; do not rebuild the index in the model. For interrupted initialization or complete-object saving, use `<work-cli> task draft-recover --input-file "<request-path>" --expected-revision <original-expected-revision>` with the original index and revision `0`, or the original `{"index": ..., "draft": ...}` object respectively. Recovery requires the complete historical index, changed draft and original prepared index bytes; it never reconstructs partial files. A successful result is `work-task-draft-recovery/v1` with `status: recovered` or `already_completed`. Read back committed progress; display copies are not updated by recovery. Unknown files, changed content, missing prepared data, changed sources or newer indexes stop recovery. Do not delete history, skip a revision or manually replace the index to bypass a rejection.
5. For addition, split or merge, present the changed boundaries and dependency impact and obtain confirmation before passing a request file containing `{"index": <next-index>, "reason": <confirmed-reason>}` to `<work-cli> task draft-list-update --input-file "<request-path>" --expected-revision <current-revision>`. Preserve existing progress metadata in the proposal; new TASKs use fresh higher IDs, `planned`, boundary revision `1` and no draft reference. Update dependencies and the current TASK explicitly. The tool retains retired IDs and historical discussions, marks affected saved discussions and their downstream consumers `needs_review`, and preserves unaffected references. Review retained decisions before reconfirming affected discussions. Display copies are not updated; use authoritative historical reads. After an interruption, separately authorize `task draft-list-recover` with the identical request and expected revision. Source snapshot changes use the separately authorized `task draft-source-update` procedure above; list and discussion saving do not replace them.
