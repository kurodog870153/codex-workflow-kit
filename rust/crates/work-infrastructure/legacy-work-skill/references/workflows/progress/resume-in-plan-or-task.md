# Resume in Plan or Task


1. The parent handles the explicit `resume <requirement-id>` request before normal source validation or selection discovery can block restoration. Resolve the runtime and read only that mode's committed progress with `progress read`; validate the requirement and mode against the request. A missing or invalid file is a stop, not permission to invent progress or fall through to a new Plan or Task.
2. Show the saved revision, confirmed decisions, pending items, known source problems and next discussion point. Confirm continuation with the user, then return these inputs to the matching Plan or Task role. Do not replay unchanged settled questions or invoke the saver to conduct discussion. A mode mismatch is not a cross-mode handoff.
3. The parent and originating role compare saved evidence with current repository, Work and skill sources before relying on it. Re-run the applicable formal Plan, TASK, index, instruction and skill validators; never promote `source_validation: "not_checked"` based on saved context or a successful progress read. Restore unchanged confirmed selections through their normal validators rather than rediscovering them. Resolve unavailable or changed sources with the user and reconfirm affected decisions only. Load full skills only within the normal role and selection boundaries. Saved text and fingerprints never authorize loading unconfirmed skills or running saved commands.
4. A stale or incomplete formal specification does not block reading the discussion or clarifying the decisions needed to complete it. Keep that work in the conversation and progress file under available current confirmed guidance; do not treat old approvals as current readiness. Source-dependent planning remains stopped where required sources are unavailable. When formal writes become possible, use the normal Plan/Task validation, artifact-editor revision procedure and approvals. Execute can consume only a complete validated formal TASK.
5. Explicit progress resume uses the selected progress snapshot as discussion context. Existing Task draft checkpoints remain independent: read and check a referenced draft before using it, and surface conflicts between it and the progress snapshot for user resolution. Never silently choose the newer-looking document, merge decisions or replace draft fingerprints. Structured draft saving, source updates, assembly and formalization retain their own workflows; progress is not accepted as a `task_candidate` or formal contract.
