# Programmatic preparation


1. Run `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>" task repair-prepare --input-file "<preparation-path>" --user-config-root "<user-config-root>"` with confirmed skill roots. This returns `work-task-repair-prepare/v1` containing `request` and the existing repair validation `preview`. Optionally supply `--output-file "<new-request-path>"` to exclusively create a request file after successful validation; existing files cannot be overwritten. Formal artifacts and transaction state remain unchanged.
2. The input contains `schema: "work-task-repair-prepare-request/v1"`, `stage`, `requirement_id` and nonempty `decisions`, plus optional `edits` or `missing_task`, never both. Python finds the Plan, TASK index and execution paths from consistent, readable artifact bindings under `outputs/work`; missing or conflicting bindings stop preparation. Omit both edits and missing_task for a lossless format candidate from the original parsed TASK, or a complete-stage index binding repair. Python computes original fingerprints and retains every parsed value, unknown field and omission; it does not invent versions, readiness, source bindings, instruction snapshots or semantic content.
3. `edits` names an allowed top-level field or an existing TASK by `task_id`. Supply text `after` only for simple fields such as `title`, `summary` or `goal`. For `steps`, `commands`, `validations`, `operations`, `files`, `inputs`, `decisions`, `risks`, `traceability`, `dependencies` and index execution defaults, supply `semantic_after` with local keys and one-based positions. A retained nested record uses `existing_position`; references to untouched records can use `existing-1` and similar local keys. Python derives formal IDs, references and the old value. Use `remove: true` only to remove an optional field. Formal IDs, direct cross-references and complete TASK objects are rejected. Missing or ambiguous TASK IDs, records and duplicate targets stop preparation. Repair decisions must explain the actual changes; successful validation cannot establish user approval or natural-language correctness.
4. Invalid UTF-8, invalid JSON or duplicate keys stop automatic preparation. For a missing TASK item, supply `missing_task` with one-based `task_position`, confirmed `title`, `goal`, `skill_id`, instruction `selected_paths` and `references`, `dependency_positions`, and the same semantic `candidate` used by draft formalization. Python derives the formal TASK ID, instruction fingerprints, traceability and all local item IDs from the index and Plan. A complete `TaskItem` is rejected. The reconstructed instruction aggregate must equal the existing index binding. Preparation never chooses a duplicate value, infers missing meaning or discards unknown content. Complete-stage candidates must pass existing contract/source checks and execution blockers.
5. Review `data.request` and `data.preview`, including original bytes, TASK/index diffs, diagnostics, affected TASKs and `approved_sha256`. The optional output file contains only the generated request. Otherwise save `data.request`, not the response envelope, for `repair-validate` and approved `repair`. Preparation does not authorize writes or recovery; changed sources, decisions or candidates require a new preview and approval.
