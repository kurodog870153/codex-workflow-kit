# Rebuild a related artifact set from semantics


1. When a Plan, TASK collection, execution index, or their bindings use an old, malformed, or internally incompatible representation, preserve the original bytes and read the current contracts and workflows before semantic reconstruction. Failed source validation is evidence, not an instruction for AI to produce replacement JSON.
2. Use `task migration-prepare` in `reconstruction` mode with the confirmed semantic Plan, ordered semantic TASKs, selection references and execution defaults. Python builds the current `v1` Plan, TASK index and items, execution index, IDs, relationships and source fingerprints together. Do not introduce a compatibility adapter or intermediate legacy document.
3. Infer only facts uniquely supported by preserved artifacts, current rules, repository evidence and confirmed decisions. Formatting, canonical ordering and derived fingerprints are Python-owned. Duplicate values, conflicting identities or missing meaning stop for one explicit user decision; never select an interpretation, invent a value or insert placeholder content.
4. Review Python's complete candidate bytes and cross-file validation. Historical Attempts and Corrections remain immutable evidence. If they cannot be preserved by the implemented semantic operation, stop and request a new prepare operation rather than overwriting them or producing JSON manually.
5. Treat the candidates as one indivisible change set. Review the complete source evidence, candidate set, cross-file diff, validation results, unresolved decisions, effects, and risks before requesting write approval. If any candidate or relationship is incomplete, keep the whole set unwritten.
6. Save the Python-prepared `data.request` and run `task migration-preview`. After reviewing its exact diff, validator results, relationships, unresolved items and fingerprint, obtain write approval bound to that fingerprint. Publish only with `task migration-apply --input-file <same-request> --approved-sha256 <fingerprint>`; do not substitute TASK repair, independent writes or an improvised script.
7. Publication stores original and candidate bytes in `<execution-dir>/.work-spec-migration-<fingerprint-prefix>.json`, publishes the full set under the shared writer mutex and records a matching `.done` marker. If interrupted, preserve all evidence and use `task migration-recover` only after separate recovery authorization, with the identical request and fingerprint.

The TASK-only procedure below remains available for its implemented scope. It does not implement the cross-file reconstruction above and must not be used to bypass that change-set boundary.
