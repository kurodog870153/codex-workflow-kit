# Use the deterministic Plan contract


1. For an initial Plan, inspect `work-plan-semantic-request/v1` through the shared contract scaffold and recursive description procedure immediately before constructing the request. Supply semantic title, summary, goals, scope, deliverables, acceptance criteria, confirmed instruction references, and the confirmed hierarchy and skill choices as `hierarchy_selection_request` and `skill_selection_request`. Then use `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>" plan semantic-prepare --input-file "<request-path>" --user-config-root "<user-config-root>"` with every confirmed `--skill-root`. Python builds and validates both selection snapshots, derives their fingerprints and the Plan artifact path, assigns item IDs and cross-references, derives the current Work instruction selection, and returns `work-plan-prepare/v1` with `plan`, `path` and `validation`. The initial semantic format links every scope and deliverable to every goal, and every deliverable to every acceptance criterion; review those relationships before approval. The old full prepare request and `plan prepare` command are unsupported. Without `--output-file`, preparation is read-only. To retain the canonical Plan candidate, add `--output-file "<new-candidate-path>"`; the parent directory must already exist, the target must not exist, and the CLI writes UTF-8 without BOM with LF on every supported platform. Never capture or transform the JSON response through shell redirection. Review the full candidate; derived `status: confirmed` is a required candidate field, not proof of approval. Existing targets are rejected. Preparation never creates the formal Plan, TASK collection, execution index or approval. Complete-object validation remains available for explicitly reviewed candidates.
2. Include validated `hierarchy_selection`, mode-resolved `work_instruction_selection`, and `skill_selection`. Before requesting authorization to create a formal Plan, save that object as the request file and invoke `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>" plan validate --input-file "<request-path>" --plan-path "<plan-path>"` with every confirmed `--skill-root`.
3. Require a successful validation result containing the canonical Plan and instruction fingerprints. Treat any nonzero exit code as a hard stop; do not repair, rewrite, retry, or reinterpret a rejected contract without new user direction.
4. After the user authorizes creation, pass the identical approved JSON request file to the same `plan create` command with every confirmed `--skill-root`. Do not assemble or write the JSON artifact manually.
5. After creation, run `plan validate --path "<plan-path>"` with the same skill roots and require the same canonical Plan, hierarchy-selection, Work instruction, and skill-selection fingerprints as the pre-write validation.
6. Never use `plan create` for an existing Plan. Keep the approved revision in the conversation and return it to the parent for the internal artifact editor's combined transaction when formal TASK and index exist.
