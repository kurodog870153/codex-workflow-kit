# Requirement artifact path validation

1. Use the shared path validator for Source, TASK and Execution. Requirement IDs must satisfy the union of Windows, macOS and Linux filename restrictions: reject ASCII controls, unsafe portable characters, trailing spaces or dots, dot/parent names and reserved Windows device names, case-insensitively and with or without an extension.
2. Defaults are `outputs/work/sources/<requirement-id>/`, `outputs/work/tasks/<requirement-id>/index.json` and `outputs/work/executions/<requirement-id>/`. The formal TASK filename must be `index.json` directly inside its requirement-ID directory; reject flat JSON, `task.json` and legacy Markdown entry points.
3. Validate the complete `artifacts` object and requirement identity before reading or writing. A confirmed custom route must supply all three project-relative paths; the TASK collection's own `artifacts.task` is authoritative. Default Source routes use `SRC-NNN/manifest.json`, its exact completed marker and the declared content file.
4. Normalize paths under actual platform behavior. Remove at most one leading `./` or `.\`; reject absolute paths, empty/dot/parent segments, requirement-ID mismatches, aliases among artifact paths and case-folded NFC portable aliases. TASK item paths are exactly `tasks/TASK-NNN.json`, matching the item ID.
5. Resolve existing paths and their nearest existing ancestors through symlinks, junctions and equivalent links. Default routes remain inside the corresponding Source/TASK/Execution boundary; custom routes remain inside the project root. Reject an unresolved or escaping path before creating a directory, record or lock.
6. Do not derive formal paths from unchecked request text, historical evidence or a supplied handoff. Validate Source triplets and every referenced TASK item through the same project-relative path boundary.
