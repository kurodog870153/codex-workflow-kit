# Artifact compatibility migration

Use `$work migration -- <request>` for existing Plan, TASK and Execute artifacts that must be compared directly with the current specification. This maintenance mode is outside the Plan → TASK → Execute lifecycle. Obtain the requirement ID and selected artifact families from the request; clarify any missing semantic choice before publication.

1. Run `work migration analyze --requirement-id <id>` with optional repeated `--artifact plan|task|execute`. Review every returned item, its source path/hash, problem and proposed content. Damaged JSON remains a review item with no automatic proposal.
2. Present each item and its proposed diff to the user. Record exactly one `apply`, `modify`, `skip`, or `abort` decision per item. `modify` supplies complete reviewed content; `skip` requires a reason. Abort ends the run before saving a request. A required Skip saves blocked audit evidence but cannot execute.
3. Build a JSON input with `schema: work-artifact-migration-decisions/v1`, the unchanged `analysis`, and `choices` containing item `id`, `action`, and optional `content` or `reason`. Save that input in the invocation transaction workspace and run `work migration prepare --input-file <path>`. The CLI rechecks source evidence and saves the final immutable request under `outputs/work/migrations/<id>/`.
4. Run `work migration preview --request-path <saved path> --approved-sha256 <request_sha256>`. Obtain approval for that exact request hash and preview. Then run `work migration apply` with the same path and hash. Execution reads only the saved request, checks source drift, validates each approved candidate, publishes each file with its own journal, and finally reconciles fingerprint references once from installed state.
5. Treat `incomplete` or `blocked` as unfinished. Preserve successful artifacts and journals. Use `work migration recover` with the identical saved request path and hash after authorizing recovery; it resumes only existing journals. Run `work migration verify --request-path <saved path> --approved-sha256 <request_sha256>` to check the published result and installed fingerprint chain. Never edit formal artifacts or request files by hand.

## Existing revision and reconstruction migration


Apply semantic reconstruction when existing related artifacts cannot satisfy the current representation as a set.

1. Read the raw source artifacts, current Plan, Task, and Execute workflows, and every current contract needed for the affected relationships. Source parsing and validation may fail; preserve those failures as evidence and continue reading any safely inspectable bytes rather than requiring a legacy object to validate.
2. Use `work migration prepare` with `work-spec-migration-prepare-request/v1`. For valid current sources, choose `mode: revision` and provide Plan path, reason and supported semantic edits. For incompatible or damaged related sources, choose `mode: reconstruction`: provide a semantic Plan with confirmed selection references, TASK title/summary, ordered semantic TASKs and optional execution defaults. TASK dependencies use earlier one-based positions; nested TASK content uses local keys and positions. The Work CLI builds formal IDs, source evidence, candidates and cross-file bindings. Do not supply complete replacement candidates or candidate bytes.
3. Separate deterministic reconstruction from semantic choice. The Work CLI applies uniquely implied structural, canonical and derived-field corrections. Return only genuine semantic alternatives to the user, with their source evidence and affected files. A reconstruction with immutable execution history or unknown TASK source files requires a dedicated semantic operation; never overwrite those files or fall back to AI-authored JSON.
4. Validate the complete candidates, not the originals, against the current per-file contracts and cross-file identities, references, fingerprints, lifecycle state, and immutable execution history. A candidate that validates individually is insufficient when another related candidate or relationship is missing.
5. Keep the Plan, TASK index and items, execution index, and any other affected formal document as one atomic candidate set. One approval must cover its exact bytes and evidence; drift, an unresolved ambiguity, or a failed relationship check invalidates the whole candidate set.
6. Save the CLI-prepared `data.request` and pass it to `work migration preview`. Only a ready report with no unresolved item may receive fingerprint-bound write approval. Use `work migration apply` with that identical request and fingerprint; use `work migration recover` only after a failed publication and separate recovery authorization. Run `work migration verify --input-file <saved request> --approved-sha256 <preview fingerprint>` after publication to check the result journal, installed candidates, and final fingerprint chain. Do not substitute manual writes or ad hoc scripts.
