# Compare raw evidence with current artifacts

1. Use `$work migration -- <request>` for existing Source/TASK/Execution artifacts or original legacy evidence that must be compared with the current contracts. Migration is a maintenance mode, separate from initial Task creation and Execute authorization. Obtain the requirement ID and clarify semantic choices before publication.
2. Run read-only `migration analyze --requirement-id <id>` with optional repeated `--artifact source|task|execute` and explicit `--evidence-path <path>` for additional original evidence. Review each source path, exact raw SHA, compatibility finding, proposed route and current contract description. A damaged or unparseable source remains evidence; it is not required to validate before reconstruction.
3. Preserve every inspected original byte and immutable Source/Attempt/Correction record. The AI compares those bytes with the current requirement, acceptance, Task and Execution contracts, records ambiguities and asks only for actual semantic decisions. Deterministic paths, canonical fields, IDs and fingerprints come from the CLI; analysis or machine proposals grant no write approval.

Analysis accepts old, unsupported, damaged and binary evidence as exact raw bytes. No historical DTO, schema alias, dual-read parser or upgrade chain is used; every reviewed replacement must validate against the sole current contract before publication.

## Ordinary artifact decisions

1. For a directly proposed compatible change, record one apply/modify/skip/abort choice per analysis item. Modify supplies complete reviewed content; skip needs a reason. Abort ends preparation. A required skip leaves the prepared run blocked, not executable.
2. Submit `work-artifact-migration-decisions` with the unchanged analysis and choices to `migration prepare --input-file <file>`. It rechecks original raw evidence and saves an immutable request under the requirement migration directory.
3. Use `migration preview --request-path <saved-path> --approved-sha256 <request-sha>` and approve that exact request and candidate set. Apply/recover/verify use the same saved path and request SHA. The owning journals preserve completed files and resume only their approved candidates; incomplete/blocked is not success.

## Semantic revision and reconstruction

1. When related artifacts need a complete new representation or semantic revision, submit strict `work-spec-migration-prepare-request` to `migration prepare --input-file <file>`. Supply requirement_id and the complete explicitly reviewed `sources` list of project-relative paths and raw_sha256. Source snapshots require the original full triplet; every existing replacement target and raw history relevant to the selected operation must be accounted for.
2. A valid baseline uses mode revision with confirmed typed semantic Specification edits. An incompatible baseline uses mode reconstruction with confirmed Task context, main acceptance, title/summary, ordered semantic TASKs and optional execution defaults. If a Source snapshot can be established, preserve its actual proof. Otherwise explicitly approve migration provenance containing the complete original raw evidence and approval SHA; do not fabricate a Source snapshot.
3. Reconstruction uses source-relative semantic TASK positions/local keys; the producer creates canonical IDs, item/index candidates, Execution bindings and source evidence. Do not submit handcrafted replacement bytes through this prepare entry or copy machine fields from stale artifacts.
4. Review prepared data.request and its complete preview, candidate diff, relationships and unresolved items. Only Task index/items and Execution index are writable candidates; immutable original sources remain evidence, not publication targets. Individual schema validity is insufficient: require complete collection, path, source, instruction/hierarchy/skill, cross-file identity, lifecycle and history validation.
5. Keep original attachments in the workspace's returned `data.paths.inputs`, semantic and CLI-prepared requests in numbered `data.paths.requests` files, and complete results in numbered `data.paths.responses` files. Create each exclusively and retain failed results under the shared transaction-workspace procedure. Save the exact CLI-prepared request and use `migration preview --input-file <file>`. A ready preview with no unresolved semantic choice may receive fingerprint-bound approval. Use `migration apply --input-file <file> --approved-sha256 <preview-fingerprint>`; this approval differs from the ordinary saved-request SHA branch.
6. Recover a partial semantic publication with the identical input and approved preview fingerprint. Recovery reconstructs the original baseline from journal evidence, rereads actual immutable sources/history and rechecks the full candidate transaction before any further write. Retain all historical bytes and partial-publication evidence; do not silently replace candidates or reuse approval after drift.
7. Run read-only `migration verify --input-file <file> --approved-sha256 <preview-fingerprint>` after publication. It checks the canonical published journal, completion marker, exact installed candidates and final source/instruction/skill/Task/Execution/history chain. Candidate installation alone is not successful verification or execution permission.

## Offline layout migration

1. `migration analyze` reports legacy locks, capture, Execute temporary files, receipts, six journal/marker layouts and retained pending workspaces. Its `legacy_layout_review_required` diagnostic includes the scoped exact raw inventory, SHA/size, directories, review-only original→candidate mappings and inventory SHA. The normal writer gate remains closed for active old/mixed layouts. A proposed path never proves current schema validity or completion.
2. The deployment owner must stop and exclude every old and current writer and disable the old binaries. Record the concrete deployment evidence. PID, elapsed time and absence of a new lock are insufficient. Recover incomplete transactions in the original environment and review command outcomes; preserve unknown effects and stop when they cannot be confirmed. Keep the original project and all Source/Attempt/Correction/approval/receipt/journal bytes unchanged. Preserve old pending workspaces in place.
3. Prepare an isolated current candidate project. Use `workspace create` and copy exact original evidence exclusively into returned `data.paths.inputs`, retaining original filenames and an explicit original→evidence path map. Verify bytes, SHA and size against the complete analyzed inventory. Do not install old locks or partial runtime files in current runtime, reinterpret old receipt/journal bytes as current evidence, or fabricate a Source/Attempt/history binding. Valid immutable formal evidence keeps its original paths and bytes; incompatible or unverified history blocks reconstruction.
4. Use the existing semantic prepare request with complete `sources` and one `semantic_decisions` item whose `id` is `offline-layout`. Its `resolution` includes `all_writers_stopped`, `old_binaries_disabled`, `pending_resolved`, `command_effects_known` (all explicitly confirmed true), non-empty `deployment_evidence`, unchanged `inventory`, `inventory_sha256`, and `evidence_mapping`. Each mapping has `original_path`, `evidence_path`, `raw_sha256`; every inventory file maps exactly once to a declared source with matching raw bytes/SHA/size. Unknown legacy classes remain blocked. Reconstruction rejects any retained Attempt/Correction/receipt history, even if an archive exists. Revision must preserve immutable Attempt/Correction files at their original formal paths as declared exact sources; a legacy receipt also requires its original complete Attempt proof. Missing or incompatible history cannot become a fresh empty Execution index. These confirmations are reviewed deployment facts, never automatic process-detection claims.
5. Review the CLI-built complete current candidate and a newly generated preview. Old approval is not current approval. The approved preview binds the offline decision and all raw evidence. Apply, recover and verify use the identical prepared request and approval; retained input evidence is rechecked along with current installed candidates. Drift, missing evidence, unresolved effects or an active legacy layout rejects publication. Migration publishes documents only; it does not launch a recorded CMD or grant Execute authorization.
6. Verify the isolated candidate and preserved originals before the deployment owner activates that candidate and keeps old binaries excluded. Cutover and original-tree retirement are deployment operations; the CLI neither deletes the old tree nor supplies a normal-writer exemption. An interrupted current publication resumes through the existing approved recover operation and retains all formal journal/marker and transport evidence.
