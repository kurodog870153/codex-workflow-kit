# Semantic cross-file migration


Apply semantic reconstruction when existing related artifacts cannot satisfy the current representation as a set.

1. Read the raw source artifacts, current Plan, Task, and Execute workflows, and every current contract needed for the affected relationships. Source parsing and validation may fail; preserve those failures as evidence and continue reading any safely inspectable bytes rather than requiring a legacy object to validate.
2. Use `task migration-prepare` with `work-spec-migration-prepare-request/v1`. For valid current sources, choose `mode: revision` and provide Plan path, reason and supported semantic edits. For incompatible or damaged related sources, choose `mode: reconstruction`: provide a semantic Plan with confirmed selection references, TASK title/summary, ordered semantic TASKs and optional execution defaults. TASK dependencies use earlier one-based positions; nested TASK content uses local keys and positions. Python builds formal IDs, source evidence, candidates and cross-file bindings. Do not supply complete replacement candidates or candidate bytes.
3. Separate deterministic reconstruction from semantic choice. Python applies uniquely implied structural, canonical and derived-field corrections. Return only genuine semantic alternatives to the user, with their source evidence and affected files. A reconstruction with immutable execution history or unknown TASK source files requires a dedicated semantic operation; never overwrite those files or fall back to AI-authored JSON.
4. Validate the complete candidates, not the originals, against the current per-file contracts and cross-file identities, references, fingerprints, lifecycle state, and immutable execution history. A candidate that validates individually is insufficient when another related candidate or relationship is missing.
5. Keep the Plan, TASK index and items, execution index, and any other affected formal document as one atomic candidate set. One approval must cover its exact bytes and evidence; drift, an unresolved ambiguity, or a failed relationship check invalidates the whole candidate set.
6. Save the Python-prepared `data.request` and pass it to `task migration-preview`. Only a ready report with no unresolved item may receive fingerprint-bound write approval. Use `task migration-apply` with that identical request and fingerprint; use `task migration-recover` only after a failed publication and separate recovery authorization. Do not substitute TASK repair, manual writes or ad hoc scripts.
