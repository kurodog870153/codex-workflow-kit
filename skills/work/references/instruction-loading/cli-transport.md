# CLI file requests and JSON responses


1. Before constructing any JSON request, identify its registered request contract from the selected workflow. If the contract ID is not explicit, run `<work-cli> contract list` and select it from the returned request entries; never infer or invent a contract ID.
2. Run `<work-cli> contract scaffold <request-contract-id>` immediately before constructing the request and use its complete scaffold, canonical key order and valid example as the structural source of truth. Run `<work-cli> contract describe <request-contract-id>` before supplying constrained fields, enumerated values or nested objects, and recursively describe every referenced contract needed to construct those values. Do not copy a stale example from instructions or guess missing, additional or natural-language values.
3. Before the first invocation of each command path in the current workflow, run that exact command path with `--help` and use the returned usage to construct its argument vector. Recheck help when the command path changes. Do not guess option names, positional arguments or option placement, and do not use a rejected invocation to discover the interface by trial and error.
4. Compare the completed request and argument vector against the fresh scaffold, descriptions and help output before invocation. A missing introspection result, unknown field or unresolved value constraint is a stop for clarification or diagnosis, not permission to submit a speculative request.
5. Every JSON request uses `--input-file "<request-path>"`. The removed `--stdin` option returns `stdin_removed` with exit code 2 and a replacement hint; no command reads stdin. Existing `--path` options still validate stored formal artifacts and are mutually exclusive with request input where applicable.
6. A request path may be absolute or relative to the process working directory, independently of `--project-root`. Prepare the complete request in the applicable transaction workspace using explicit UTF-8 encoding. Accept no BOM or exactly one leading UTF-8 BOM; reject other encodings or repeated BOMs. Request files are transport inputs, not formal artifacts or discussion checkpoints. Preserve the identical approved request file for apply or separately authorized recovery. Preparing a request does not publish a candidate or authorize its operation.
7. Invoke one CLI command at a time. On Windows and macOS, quote paths containing spaces and avoid shell chaining, pipes, redirection, heredocs and environment-variable expansion. Python callers pass an argument array to `subprocess.run` with `shell=False`, `capture_output=True`, explicit UTF-8 decoding and a timeout; do not build a shell command string or send JSON through stdin.
8. Each completed CLI invocation emits exactly one UTF-8 JSON object to stdout, including usage errors, handled failures and `--help`. Its schema is `work-cli-result/v1`, with exactly `schema`, `status`, `reason_code`, `message` and `data`. Successful commands use exit code 0, status `success` and reason `ok`; an operation already reporting `already_completed` uses that status and reason with exit code 0. Rejected inputs or workflow gates use `rejected`; I/O and internal failures use `failed`. Nonzero exit codes retain their existing meanings, and `reason_code` retains the specific error identifier. Error details are in `data`. Stderr is reserved for additional diagnostics.
9. Read the exit code and parse stdout on both success and failure; never substitute stderr for the result. Check the envelope before consuming `data`. All command-specific schemas, fields and statuses mentioned in workflows refer to successful response `data`, not the outer envelope. Render commands put the document itself in `data`: preserve its key order and canonical serialization when using it, and never save or hand off the response envelope as a formal document. Formal output remains UTF-8 without BOM, NFC, LF and one trailing LF.
10. An empty or malformed stdout is a transport failure: report the exit code, stderr diagnostics and a command summary without request contents. On timeout, interruption or forced termination, do not infer success or automatically retry a mutating command; retain the request and inspect transaction evidence under the existing recovery rules.
