# Coordinated formal artifact revision


Apply this section only when confirmed discussion requires revision of existing formal Plan, TASK and execution-index artifacts together. Independent discussion progress, initial artifact creation, Task checkpoint approval and source updates, skill selection, normal cross-session handoffs and execution authorization retain their own workflows. A checkpoint is not a formal TASK.

1. The selected Plan, Task coordinator or Execute role returns the complete confirmed request, decisions, requirement ID, all three artifact paths, affected TASK IDs, confirmed hierarchy and skill selections, repository evidence and original continuation point to the parent. Task skill subagents return impact through their coordinator. None of these roles spawns the editor or expands its own write scope.
2. The parent pauses the selected role and reads the private artifact editor prompt. Run exactly one ephemeral editor using that prompt's required runtime configuration. If the required capability, model or reasoning configuration is unavailable, follow the prompt directly with the current runtime. Supply `WORK_ARTIFACT_EDIT_V1`, `skill=$work`, `origin_mode=<plan|task|execute>`, resolved skill/project roots, this shared source and all retained inputs from the preceding step. Only the parent invokes the editor; it cannot spawn children.
3. Keep goals, scope, deliverables and acceptance in Plan; technical decisions, future steps, CMD/OP/VAL specifications and execution settings in TASK. The CLI derives index identities and statuses. The editor applies confirmed discussion to those documents; it returns new requirement or acceptance decisions for Plan discussion and new technical or specification decisions for Task discussion through the parent. Loading Execute guidance permits checking document consistency, not implementation, Attempt/Correction creation or execution-history edits.
4. The editor owns the combined read-only preview and authorized specification transaction under the specification revision workflow. For execution-deviation reconciliation, preserve the immutable closed Attempt and use its dedicated reconciliation preview before the nested migration transaction. Review the complete candidate set, affected TASKs, downstream impact, exact commands, validation, risks and any requested discussion checkpoint before one continuation approval. Bind that approval to the applicable specification or reconciliation fingerprint and, when a checkpoint is included, its separately prepared progress fingerprint. Reuse approval only for those identical previews. Approval of requirements or delegation is insufficient. After approval, continue through publication, read-only verification and the prevalidated checkpoint save without another routine confirmation. CLI-owned transaction records, temporary files, lock, writer mutex and completion marker are permitted only as necessary for that transaction.
6. Relay unresolved questions and confirmed answers through the parent to the same editor, preserving the saved discussion. Do not ask for a user-facing mode switch or copied handoff JSON for this same-session revision. Reject `$work artifact-editor`, `$work edit` and direct invocation of a private prompt.
7. Return the result to the original role at its retained continuation point. Reload and revalidate changed sources before continuing; Execute must still perform normal preflight. Preserve active execution locks and historical Attempt/Correction files. A successful revision never authorizes implementation or a new Attempt. If publication, verification, document synchronization or checkpoint saving fails or observes drift, stop immediately, preserve the complete transaction workspace, and return the failed step, observed evidence, completed writes and available separately authorized recovery choices to the user. Do not retry, roll back, recover or continue later steps automatically.
