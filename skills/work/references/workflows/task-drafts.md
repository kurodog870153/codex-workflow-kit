# Task draft checkpoints

Use this reference for the initial TASK list, an authorized checkpoint, or a
new-session resume. `<work-cli>` means the resolved Python command and
`<skill-root>/scripts/work.py --project-root <project-root>`.

For a user-requested independent discussion save or explicit `resume` request,
use [discussion progress](progress.md) through the parent's private progress saver.
It can preserve unfinished decisions when these structured drafts' formal-source
checks block work. It neither replaces this index nor authorizes source updates,
draft assembly or formalization.

## Read and verify

1. Read the current index with `<work-cli> task draft-read --requirement-id <requirement-id>`. This reads only the authoritative index and its historical copy, not all TASK discussions.
2. For a saved discussion, run the same command with `--task-id TASK-001`, substituting the selected ID. The CLI follows `draft_ref` and verifies the exact historical bytes. Never use the root-level `TASK-001.json` display copy as resume evidence.
3. Before relying on saved decisions or writing a checkpoint, run `<work-cli> plan validate --path <plan-path> --user-config-root <user-config-root>` with every confirmed source `--skill-root`. Compare the returned `plan_sha256`, `hierarchy_selection_sha256` and `skill_selection_sha256` with index `source`. Storage integrity alone does not verify live sources or authorize a write.
4. Reconstruct the current TASK's confirmed hierarchy subset and routed references from its saved decisions and source Plan. Run `<work-cli> task draft-check --requirement-id <requirement-id> --task-id <task-id> --expected-revision <index-revision> --plan-path <plan-path> --user-config-root <user-config-root>` with every confirmed `--skill-root`, each applicable `--reference`, and either explicit `--general-only` or repeated `--instruction-path <confirmed-path>`. Require `work-task-draft-source-check/v1` with `status: valid`. This read-only check performs the Plan fingerprint comparison, skill binding check, hierarchy-subset validation and current instruction fingerprint comparison, and rejects an index changed during the check. It does not authorize saving or prove repository evidence is current. If the exact prior selection is unavailable, ask for confirmation instead of guessing paths or replacing the fingerprint.
5. Load only the selected TASK's applicable instructions and one assigned full skill. Other TASKs contribute only necessary boundaries and dependency summaries; do not preload their full skills, drafts or session transcripts. Index skill IDs must remain in the validated Plan selection.
6. Any source drift or ambiguous selection stops dependent discussion and saving. Identify affected decisions and confirm the new source/selection and the update operation first. Pipe `{"reason": <confirmed-reason>, "selections": {"TASK-001": {"selected_paths": [], "references": []}, ...}}` to `<work-cli> task draft-source-update --stdin --requirement-id <requirement-id> --expected-revision <current-revision> --plan-path <plan-path> --user-config-root <user-config-root>` with all Plan `--skill-root` values. Every active TASK needs an explicit selection. The tool revalidates the Plan and skills and derives fingerprints; it cannot repair a stale formal Plan or replace an unavailable skill binding. Shared source changes mark all existing discussions for review; a local instruction change marks that TASK and its downstream consumers. Retain their old decisions as review evidence, not current approval. Before resuming formalization, reconfirm affected decisions and update structured candidates. After an interrupted update, separately authorize `task draft-source-recover` with the identical request and original expected revision; recovery rejects changed sources or incomplete files. Display copies are not updated. Never overwrite hashes manually to bypass a failure.

## Initialize and save

1. Initialize by piping a complete `work-task-planning-index/v1` JSON object to `<work-cli> task draft-init --stdin`. Obtain confirmation of the list and save first. Use revision `1`, all entries `planned`, and no `draft_ref`. The contract module defines the exact fields; no formal TASK, execution index or Attempt is created.
2. The index stores requirement ID, source fingerprints, current TASK and boundaries (`id`, `title`, `goal`, `scope`, `skill_id`, direct `dependencies`, planning `status`, `boundary_revision`, `instructions_sha256`). Keep the selected hierarchy paths and routed reference names explicit in the corresponding discussion notes/decision rationale so a future session can reconstruct the selection. If needed before a first discussion exists, obtain that selection again at resume.
3. Keep each discussion as `work-task-draft/v1`: save detailed `notes`, `confirmed_decisions` with `statement` and `rationale`, `tentative`, `open_questions`, and `next_discussion_point`. Preserve concrete file, command, validation and instruction-selection details needed later; do not substitute a vague summary or put unconfirmed proposals among confirmed decisions.
4. Save by piping exactly `{"index": <next-index>, "draft": <one-draft>}` to `<work-cli> task draft-save --stdin --expected-revision <last-read-index-revision>`. Increment the index revision once and the selected draft revision once (first draft is `1`). Preserve other TASK entries and existing references. Storage generates the selected `draft_ref` from the saved bytes.
5. Use `in_progress` for unfinished discussion and provide a next discussion point. Use `refined` only after the discussion has been confirmed, with no tentative items, open questions or next discussion point. `refined` records discussion progress, not formal readiness or execution permission.
6. Before a write, summarize its target files, operation and verification along with the content being confirmed. User-requested mid-discussion saving preserves undecided content as undecided; it does not require completing the TASK first. Do not save on every turn or automatically impose a token threshold.
7. Verify the save result and read back the committed index and current draft. Report the save revision and resume command, then stop at the checkpoint. New-session confirmation checks progress without asking the user to repeat unchanged decisions.

## File and failure semantics

1. The effective entry point is `outputs/work/tasks/<requirement-id>/drafts/index.json`. Each entry's `draft_ref` contains `save_revision`, draft `revision` and `sha256`; the historical path is `history/<save_revision>/<TASK-ID>.json`.
2. Every save exclusively reserves `history/<index-revision>/`, writes its index and changed draft, verifies bytes, and atomically switches the effective index. Unchanged drafts retain their earlier references. The root-level `<TASK-ID>.json` is a display copy only.
3. A successful save with `mirror_status: stale` is committed despite the outdated display copy. Report that condition and continue to use historical reads. `superseded` means a newer index was observed; read current progress before another write.
4. A nonzero exit is a stop. A stale revision requires reading and reviewing the new progress, not blindly retrying. `draft_save_interrupted` preserves the previous committed index and may leave a reserved history directory. After separate user authorization, pipe the identical original request to `<work-cli> task draft-recover --stdin --expected-revision <original-expected-revision>`. For interrupted initialization, pass the original index and revision `0`; for an interrupted save, pass the original `{"index": ..., "draft": ...}` object. Recovery requires the complete historical index, changed draft and original prepared index bytes; it never reconstructs partial files. A successful result is `work-task-draft-recovery/v1` with `status: recovered` or `already_completed`. Read back committed progress; display copies are not updated by recovery. Unknown files, changed content, missing prepared data or newer indexes stop recovery. Do not delete history, skip a revision or manually replace the index to bypass a rejection.
5. For addition, split or merge, present the changed boundaries and dependency impact and obtain confirmation before piping `{"index": <next-index>, "reason": <confirmed-reason>}` to `<work-cli> task draft-list-update --stdin --expected-revision <current-revision>`. Preserve existing progress metadata in the proposal; new TASKs use fresh higher IDs, `planned`, boundary revision `1` and no draft reference. Update dependencies and the current TASK explicitly. The tool retains retired IDs and historical discussions, marks affected saved discussions and their downstream consumers `needs_review`, and preserves unaffected references. Review retained decisions before reconfirming affected discussions. Display copies are not updated; use authoritative historical reads. After an interruption, separately authorize `task draft-list-recover` with the identical request and expected revision. Source snapshot changes use the separately authorized `task draft-source-update` procedure above; list and discussion saving do not replace them.

## Formalization boundary

1. Store each discussed formal TASK object in the optional `task_candidate` field of its draft. Before assembly, every active discussion must be `refined` and contain this object, with the same ID, title, goal, skill, dependencies and instruction fingerprint as its boundary. Notes alone are insufficient. After list changes, review and update the retained candidate before reconfirming the discussion.
2. Pipe document metadata (`title`, `summary`, optional `execution_defaults` and shared `decisions`) to `<work-cli> task draft-assemble --stdin --requirement-id <requirement-id> --expected-revision <index-revision> --plan-path <plan-path> --user-config-root <user-config-root>` with every Plan `--skill-root`. This read-only command derives paths and source data from the Plan, loads all active structured candidates, and validates the complete initial contract. Review the returned contract's outcomes, file operations, commands and validations with the user; obtain explicit formal approval tied to `approval_sha256`. Do not repeat the full JSON on every discussion turn.
3. After approval, use `task draft-create` with the identical metadata and arguments plus `--approved-sha256 <approved-fingerprint>`. It reassembles and revalidates before creating the formal TASK and execution index; the fingerprint binds both the planning snapshot and canonical contract. A hash is evidence of unchanged content, not authorization by itself. Changed sources, unresolved discussion, missing fields or fingerprint mismatch stop creation. An existing formal TASK is not overwritten. Partial formal creation continues to use the separately authorized `task recover-create` procedure with the identical approved assembled contract.
4. Formal output remains `outputs/work/tasks/<requirement-id>/task.json`. Draft checkpoints and session changes do not authorize creating it or its execution index. Assembly creates only the initial specification; revising an existing formal specification uses the existing specification-update workflow.
