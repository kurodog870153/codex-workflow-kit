# Use deterministic handoffs


Apply the shared handoff procedure for transport, source verification, legacy evidence and authorization boundaries.

1. Before using `task_to_execute`, save the received JSON unchanged as the request file and invoke `<work-cli> handoff verify-task-to-execute --input-file "<request-path>" --task-path "<confirmed-task-path>" --task-id <confirmed-task-id> --user-config-root "<user-config-root>"` with every confirmed `--skill-root`. Use the explicitly selected formal TASK path and TASK ID, not targets chosen solely from the incoming handoff. Require `work-handoff-source-validation/v1` with `status: valid`. The command validates the current TASK and source Plan, rejects incomplete specification transactions, and compares requirement ID, artifact paths, specification and TASK IDs, task-specific instruction fingerprint, skill ID and source fingerprints. Reject stale or mismatched handoffs without rewriting their fields. This verifies source identity, not semantic approval; it does not replace preflight, worktree review or authorization to start an Attempt.
2. For a specification defect requiring a cross-session handoff with an existing stopped or blocked Attempt, save a JSON request file containing only `summary`, `reason` (the specification defect explanation), `confirmed_approach`, `requested_changes`, `preserve`, `affected_ids`, and `validation_requirements` and invoke `<work-cli> handoff build-execute-to-task --input-file "<request-path>" --task-path "<task-path>" --task-id <TASK-ID> --attempt-id <ATTEMPT-ID> --user-config-root "<user-config-root>"` with every confirmed `--skill-root`; use `build-execute-to-plan` when returning to Plan. The command validates the latest closed Attempt against TASK, Plan, index, and current instruction/skill fingerprints, and derives the machine fields. A blocked Attempt's recorded closing reason remains unchanged; `reason` explains why the requested return concerns a specification defect. Require success before relaying the result. Confirmed same-session revisions use the internal editor above.
3. For a cross-session specification handoff before any Attempt exists for the target TASK, use the same semantic request and command with `--preflight` instead of `--attempt-id`. The command requires a valid Plan, TASK, and index, an initial `pending` TASK, no lock or transaction residue, and an absent or empty target TASK execution directory. It derives `attempt: {"status": "not_created"}` and `phase: preflight`; never supply those fields yourself. It validates source identity without requiring inputs, dependencies, or file readiness to pass, and does not classify a preflight failure as a specification defect automatically. `reason` must explain that judgment. Existing Attempt history must use the closed-Attempt path. A successful handoff is not a successful eligibility check or permission to resume execution.
