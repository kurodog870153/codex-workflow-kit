# Apply one Attempt authorization boundary


1. Before starting an Attempt, present one complete authorization summary covering the target TASK, files, formal CMDs, OPs and VALs, expected side effects, external operations, risks, validation and normal Attempt closure. Bind authorization to that exact reviewed scope and the current worktree snapshot. Platform or sandbox permission remains independently required when the runtime requests it; an Attempt authorization never substitutes for platform permission.
2. After the Attempt starts, do not ask again before `record-begin`, execution, `record-finish`, routine validation or normal `attempt-close` when the exact operation and effects remain inside that authorization. These state transitions still perform every source, lock, fingerprint and recovery check; absence of another conversational confirmation is not permission to widen their scope.
3. Stop and obtain a new decision before any unlisted file, command capability, external operation or side effect; any source or worktree drift that invalidates the reviewed scope; any uncertain result; any retry not already fixed by the TASK and authorization; or any recovery. A new decision may authorize only the reviewed addition or direct a specification return; it does not silently replace the original TASK.
4. When execution discovers an insufficiency, submit `work-execution-deviation-semantic-request/v1` to `execute deviation-prepare-semantic` while the affected record remains reserved. Describe the gap, semantic action, supplemental file scope, semantic impact and side effects. For example, `{"kind":"replace_command","replacement":{"mode":"argv","argv":["tool","test"]}}` contains no record ID. Use one-based `command_positions`, `validation_position`, `command_position` and `acceptance_positions` to refer to existing items in the current TASK when adding a validation or adjusting an operation. Never supply formal IDs or direct ID references in the semantic action. Python derives the TASK, Attempt, reserved record and formal task basis from the active lock and TASK, allocates new command or validation IDs, resolves positions, and runs the existing full proposal validation. Review the returned complete proposal, action, semantic impact, side effects, classification, blocking flag, source fingerprints and `preview_sha256`; save its exact `proposal` for `deviation-record`. The old full-proposal preparation command is unsupported. Do not reuse the original Attempt authorization as approval for this runtime discovery.
5. After fresh approval of that exact preview, run `execute deviation-record` with the approved fingerprint and the new authorization evidence. The recorded deviation contains an immutable supplemental authorization binding the approved preview, exact action, explicitly reviewed supplemental file scope and fresh evidence. An omitted legacy file scope is empty. Source, proposal, action, file scope or fingerprint drift requires a new preview and approval.
6. For a recorded non-blocking deviation, keep the same Attempt and reserved record. `record-begin`, command preview and execution, and `record-finish` resolve the effective record, operation, command, authorization evidence and applicable file scope from the original Attempt plus that exact supplemental authorization. An approved `skip_record` finishes the reserved record only with canonical skipped evidence bound to the same record ID, reason and deviation ID; it is completion evidence, not a successful execution result. Duplicate targets, mismatched anchors, blocking actions and any unapproved record or file remain hard stops. For a recorded blocking deviation, do not revise Plan or TASK first: stop further execution, close the Attempt as a specification defect through the permitted blocking-close path, then enter reconciliation.
7. After close, begin review of unresolved deviations with `task reconciliation-prepare`, supplying the closed Attempt path and confirmed semantic choice and edits. Save its Python-prepared `data.request`, run `task reconciliation-preview`, then bind approval to the complete reconciliation fingerprint and publish with `task reconciliation-apply`. `retain_only` publishes only the ledger through a recoverable transaction; other choices publish the reviewed specification candidates and ledger together. The ledger records incorporated, retained and declined outcomes without rewriting the closed Attempt, and workflow routing excludes those resolved IDs. Recover an interrupted transaction only through its separately authorized recovery command.
