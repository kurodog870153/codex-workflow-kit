# Specification verification

1. After successful ordinary `specification apply` or authorized recovery, transport the returned `verification_request` unchanged to read-only `specification verify --input-file "<request-path>" --user-config-root "<user-config-root>"` with identical project and skill roots. No routine additional confirmation is needed within an already authorized continuation.
2. The ordinary request identifies the requirement, Source/TASK/Execution artifact paths and actual record ID. Verification checks the canonical journal and completion marker, exact installed TASK collection and Execution bytes, immutable Source proof, instruction/skill bindings, derived transaction evidence and preserved execution history.
3. Semantic migration uses its unchanged approved prepared request and fingerprint with `migration verify`. Its verifier reconstructs the original reviewed baseline, verifies installed candidates and the complete current TASK/Execution chain, and checks actual retained history. Reconciliation publication/recovery additionally checks the exact ledger and closed Attempt approval; retain its publication evidence rather than inventing an ordinary verification request.
4. Ordinary success returns `verified: true`, scope `exact_specification_result`, `execution_authorized: false` and `normal_execute_preflight`. Required failed checks remain errors with the complete report. A later legitimate revision or history change may make an old verification record inapplicable; inspect the cause instead of rolling back or reusing stale approval.
5. Verification is read-only and does not grant Execute approval, alter Source/formal artifacts/history/Git state or restore invalidated acceptance results. A new Attempt still requires normal Execute preflight and its own authorization boundary.
