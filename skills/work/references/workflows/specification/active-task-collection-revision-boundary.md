# Active TASK collection revision boundary

1. The validated TASK collection's `artifacts.task` selects its formal `index.json`; every referenced item belongs to that collection. Single-file `task.json` is unsupported. Source Snapshot evidence is immutable and verified from its actual bytes, manifest and completion marker.
2. A specification revision validates the complete TASK collection and synchronized Execution index, even when only one item changes. Edits target `task_index` or `task_item`; item edits identify the exact `task_id`. Derived references, IDs, fingerprints, instruction selections and Execution states come from Work CLI.
3. A Source replacement requires the exact previous planning fingerprint, new Source fingerprint, complete requirement review, retained/removed/added main acceptance IDs and an impact review for every existing TASK. Preserve the previous Snapshot. A replacement does not authorize implementation or execution.
4. Rebuild main acceptance aggregation and invalidate only evidence affected by the approved change, including dependent TASKs. Preserve unaffected evidence and all historical Attempt and Correction bytes. Unchanged items retain their exact bytes and fingerprints.
5. The journal binds original/proposed TASK item, index, Execution and optional ledger bytes, affected TASKs, Source proof, preserved history, request and approval. Its completion marker binds the canonical journal fingerprint. Publish item bytes before the formal index commit point, then the synchronized Execution index and completion marker.
6. Publication is a recoverable logical transaction. An incomplete record blocks Execute. Recovery advances only exact recognized original, approved final or recoverable missing states; conflicting bytes stop recovery. Preserve transaction evidence for removed items and never destructively clean history.
