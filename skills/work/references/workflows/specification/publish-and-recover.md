# Publish and recover

1. Obtain or reuse continuation approval bound to the complete reviewed candidates and fingerprint. Bind a separately included progress checkpoint to its own displayed fingerprint. Run `specification apply --input-file "<request-path>" --approved-sha256 <approved-sha256>` with the same project, user configuration and skill roots. Changed Source proof, instructions, candidate bytes or history invalidates approval.
2. Work mutations share the process-released OS mutex `.work-state-writer.lock` and recheck approved evidence under the lock. Keep unrelated editors paused during publication. Work CLI derives the transaction namespace and preserves original/proposed bytes. It publishes TASK items, the collection index and synchronized Execution state before the fingerprinted completion marker. Execute stays blocked while a transaction is incomplete.
3. For reconciliation use `specification reconciliation-apply` on the saved preview request. `retain_only` writes only its approved ledger; incorporation publishes the complete approved TASK/Execution migration set and ledger. The same closed Attempt evidence and reconciliation fingerprint are checked under the writer lock. Immutable Source and historical Attempt/Correction bytes are preserved.
4. Require the successful publication result and retain its journal, completion marker, affected TASKs and checks. Use `--verbose` for complete evidence. Ordinary revision returns a read-only verification request; migration publication validates the resulting candidate chain. Publication does not execute CMD, OP, VAL or implementation.
5. On interruption preserve all current files, journals, temporary bytes and history. Report the observed state and obtain recovery authorization when it is outside the existing authorization. Use the identical request, roots and fingerprint with `specification recover` or `specification reconciliation-recover`; choose the command that created the transaction.
6. Recovery revalidates exact original/candidate contracts, Source proof, instructions, approved request and history. Reconciliation reconstructs the original ledger and Execution baseline from the canonical journal and checks the real closed Attempt. It resumes only the same approved file set and cannot revive invalidated acceptance evidence. Repeated recovery verifies the already-published result.
7. Recoverable partial writes may advance only to their exact approved bytes. Conflicting bytes, changed instructions/history, unresolved or competing journals remain stops. Never roll back, overwrite a conflict, delete history or start execution. Return to the originating workflow with retained discussion and revalidate its current Source; stale draft checkpoints need separately authorized review.
