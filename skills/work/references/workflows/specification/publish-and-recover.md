# Publish and recover

1. Obtain or reuse continuation approval bound to the complete reviewed candidates and fingerprint. Keep bounded DiscussionSession saving separate from the formal publication approval. Run `specification apply --input-file "<request-path>" --approved-sha256 <approved-sha256>` with the same project, user configuration and skill roots. Changed Source proof, instructions, candidate bytes or history invalidates approval.
2. Work mutations use `outputs/work/runtime/locks/<requirement-id>/execution.lock`, derived from the verified requirement and canonical project root, including custom Execution paths. Exclusive creation records a unique owner; Work CLI rechecks approved evidence under that owner and explicitly releases only its own lock after success or a controlled error. A killed process leaves blocking owner evidence. Unknown owners and legacy writer locks require reviewed offline handling with all writers stopped; age, PID and an unlocked old OS mutex never authorize removal. Keep unrelated editors paused during publication. Work CLI preserves original/proposed bytes and publishes TASK items, the collection index and synchronized Execution state before the fingerprinted completion marker. Execute stays blocked while a transaction is incomplete.
3. For reconciliation use `specification reconciliation-apply` on the saved preview request. `retain_only` writes only its approved ledger; incorporation publishes the complete approved TASK/Execution migration set and ledger. The same closed Attempt evidence and reconciliation fingerprint are checked under the writer lock. Immutable Source and historical Attempt/Correction bytes are preserved.
4. Require the successful publication result and retain its journal, completion marker, affected TASKs and checks. Use `--verbose` for complete evidence. Ordinary revision returns a read-only verification request; migration publication validates the resulting candidate chain. Publication does not execute CMD, OP, VAL or implementation.
5. On interruption preserve all current files, journals, temporary bytes and history. Report the observed state and obtain recovery authorization when it is outside the existing authorization. Use the identical request, roots and fingerprint with `specification recover` or `specification reconciliation-recover`; choose the command that created the transaction.
6. Recovery revalidates exact original/candidate contracts, Source proof, instructions, approved request and history. Reconciliation reconstructs the original ledger and Execution baseline from the canonical journal and checks the real closed Attempt. It resumes only the same approved file set and cannot revive invalidated acceptance evidence. Repeated recovery verifies the already-published result.
7. Recoverable partial writes may advance only to their exact approved bytes. Conflicting bytes, changed instructions/history, unresolved or competing journals remain stops. Never roll back, overwrite a conflict, delete history or start execution. Return to the originating workflow with retained discussion and revalidate its current Source; stale Session planning needs explicit semantic review.
8. Retain formal evidence under the verified Execution directory: `journals/specification-update/<SPEC-UPDATE-ID>/journal.json`, `journals/specification-migration/<APPROVAL12>/journal.json`, its `items/<NNN>/journal.json` and `reconcile/journal.json`. Each leaf retains `committed.sha256`, the exact SHA-256 of the published journal followed by a newline. The original full approval and item position remain authoritative; a matching short directory name grants no recovery authority. Instruction migration and Source refresh journals use `journals/instruction-migration/<PREVIEW12>/journal.json` and `journals/source-refresh/<PREVIEW12>/journal.json` for approved recovery only. The immutable Source completion marker remains `manifest.json.done`.
9. Prepared evidence belongs to `outputs/work/runtime/staging/<requirement-id>/<operation>/<transaction-identity>/`: `transaction.json`, fixed final `journal.json.tmp` and numbered `targets/<n>.tmp`. Recovery validates the complete canonical Root, requirement, Execution scope, approval, frozen original/candidate bytes, inventory and observed publication order under the Native owner. Missing or truncated formal evidence requires the matching complete manifest. After all formal bytes and the retained marker are reread and verified, clean only that transaction's verified staging payloads and remove its manifest last. Failed cleanup keeps recovery identity; completed journal and marker remain.
10. History includes immutable Attempt, Correction and command receipt bytes and separately verified completed journal/marker bytes. Exclude only the current reviewed transaction family to avoid an approval referring to its own journal. A Migration batch may retain an interrupted sibling only when the complete saved request, all item originals/candidates and full frozen manifests bind that sibling under the same Native owner. Unknown items, another approval sharing the short prefix, unrelated staging, legacy layout or conflicting formal evidence block publication. Recovery preserves earlier completed items and resumes the identical approved batch.
