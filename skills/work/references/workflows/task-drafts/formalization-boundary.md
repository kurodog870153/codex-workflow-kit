# Formalization boundary


Before a confirmed list addition, split, merge or boundary edit, use read-only `task semantic-prepare --expected-revision <revision> --input-file "<request-path>" --requirement-id <requirement-id> --plan-path "<plan-path>" --user-config-root "<user-config-root>"` with confirmed skill roots. The semantic request contains `upsert`, `remove_task_ids`, `current_task` and a non-empty `reason`. Identify edited existing boundaries with `existing_task_id`; omit it for new boundaries. Each dependency and `current_task` uses exactly one `existing_task_id` or one-based `upsert_position`. Python assigns new IDs above all active and retired IDs and resolves dependencies. Omit unchanged TASKs; explicitly upsert any surviving TASK whose dependencies must change after a split or merge. Existing selections are preserved; new TASKs require an explicit confirmed selection, while selection changes require `draft-source-update`. Removed IDs must currently exist, and no ID may be both removed and updated. The tool does not decide split or merge semantics.

The preview returns the exact full-object `request` accepted by `draft-list-update`, the resulting `index`, affected TASK IDs and changed `drafts`. Review all effects and preserve decisions marked for review. Save `data.request`, not the preview index (whose progress metadata is already advanced), and follow the existing separately approved list-update/recovery procedure with the same expected revision. Preparation preserves untouched entries and historical references, derives revisions and retired IDs through the existing list logic, checks current sources, and writes nothing. Source validation is a snapshot: recheck current sources before applying; approval and recovery remain separate. Never treat a preview as formal readiness.

1. Store only semantic TASK content in the optional `task_candidate` field: required `steps` and `validations`, with relevant `files`, `commands`, `decisions`, `inputs`, `risks` or `operations`. Each item has a lowercase local `key`, never a formal ID. STEP `references` use `{kind, key}` for a TASK-local group; VAL uses `command_keys` and one-based `acceptance_positions`; OP uses `validation_key` and optional `command_key`; a `task_output` input uses `dependency_position` and `file_key`. Python allocates all formal IDs and resolves references from the current Plan and TASK boundaries. Do not include direct ID references, ID, title, goal, skill, dependencies, instruction selection or traceability. Before assembly, every active discussion must be `refined` and contain this object. Notes alone are insufficient. After list changes, review the retained candidate before reconfirming the discussion. The initial assembly links each TASK to all Plan goals, deliverables and acceptance criteria; review these broad traceability links before formal approval.
2. Pass a request file containing document metadata (`title`, `summary`, optional `execution_defaults` and shared `decisions`) to `<work-cli> task draft-assemble --input-file "<request-path>" --requirement-id <requirement-id> --expected-revision <index-revision> --plan-path "<plan-path>" --user-config-root "<user-config-root>"` with every Plan `--skill-root`. This read-only command derives paths and source data from the Plan, loads all active structured candidates, and validates the complete initial contract. Review the returned contract's outcomes, file operations, commands and validations with the user; obtain explicit formal approval tied to `approval_sha256`. Do not repeat the full JSON on every discussion turn.
3. After approval, use `task draft-create` with the identical metadata and arguments plus `--approved-sha256 <approved-fingerprint>`. It reassembles and revalidates before creating the formal TASK collection and execution index; the fingerprint binds both the planning snapshot and canonical logical contract. A hash is evidence of unchanged content, not authorization by itself. Changed sources, unresolved discussion, missing fields or fingerprint mismatch stop creation. An existing formal TASK is not overwritten. Partial formal creation continues to use the separately authorized `task recover-create` procedure with the identical approved assembled contract.
4. Formal output uses `outputs/work/tasks/<requirement-id>/index.json` plus referenced `tasks/TASK-NNN.json` items. This differs from the planning `drafts/index.json` and execution `index.json`. Draft checkpoints and session changes do not authorize creating the formal collection or its execution index. Assembly creates only the initial specification; revise an existing specification through the specification-update workflow.
