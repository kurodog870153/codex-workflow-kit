# Initialize and save


For initial planning, use read-only `task semantic-prepare --input-file "<request-path>" --requirement-id <requirement-id> --plan-path "<plan-path>" --user-config-root "<user-config-root>"` with all confirmed `--skill-root` values. Supply `upsert`, empty `remove_task_ids`, an explicitly chosen `current_task` (or `null`), and `reason: null`. Each new item contains `title`, `goal`, `scope`, `skill_id`, `instruction_selection` with ordered `selected_paths` and `references`, and `dependencies`. Each dependency and `current_task` references an item by one-based `upsert_position`; do not supply a TASK ID, revision, status, hash or draft reference. The command derives IDs and metadata, validates the live Plan and selections, and returns a read-only `work-task-draft-prepare/v1` preview. Review its complete `request` index before separately authorizing publication with `draft-init`; a changed source requires renewed review. Existing storage or interrupted residue is a stop. On a handled save failure, preserve the exact reviewed index for separately authorized `draft-recover --expected-revision 0`; do not rebuild the recovery object.

1. Initialize by passing a request file containing a complete `work-task-planning-index/v1` JSON object to `<work-cli> task draft-init --input-file "<request-path>"`. Obtain confirmation of the list and save first. Use revision `1`, all entries `planned`, and no `draft_ref`. The contract module defines the exact fields; no formal TASK, execution index or Attempt is created.
2. The index stores requirement ID, source fingerprints, current TASK and boundaries (`id`, `title`, `goal`, `scope`, `skill_id`, direct `dependencies`, planning `status`, `boundary_revision`, `instructions_sha256`). Include each confirmed `instruction_selection` as `{"selected_paths": [...], "references": [...]}` on its TASK entry, including empty arrays for explicitly confirmed general-only without references. The index is the single structured source; do not duplicate this field in discussion drafts. Existing entries without it remain readable. The first authorized `draft-save-request` with an explicit selection verifies its fingerprint and records it without changing the boundary revision. Source updates record their revalidated selections; list updates preserve selections of existing TASKs. Never edit old history to add the field.
3. Keep each discussion as `work-task-draft/v1`: save detailed `notes`, `confirmed_decisions` with `statement` and `rationale`, `tentative`, `open_questions`, and `next_discussion_point`. Preserve concrete file, command, validation and instruction-selection details needed later; do not substitute a vague summary or put unconfirmed proposals among confirmed decisions.
4. Save one complete discussion by passing a request file containing `{"status": <in_progress|refined|needs_review>, "notes": [...], "confirmed_decisions": [...], "tentative": [...], "open_questions": [...], "next_discussion_point": <text-or-null>}` with optional semantic `task_candidate` to `<work-cli> task draft-save-request --input-file "<request-path>" --requirement-id <requirement-id> --task-id <task-id> --expected-revision <last-read-index-revision> --plan-path "<plan-path>" --user-config-root "<user-config-root>"`. A refined candidate requires `steps` and `validations`; nested items use local lowercase `key` and semantic references as specified in the formalization boundary, never formal IDs or direct ID references. Include all confirmed `--skill-root` values. Omit selection flags when the TASK already stores its selection; entries without one need the complete explicit selection described for `draft-check`. The command checks live sources, records the selection and derives both revisions, source fields, boundary revision, current TASK and `draft_ref`, preserving every other TASK. Send the full selected discussion content, not a patch: omitted `task_candidate` is not retained. Do not send an index, hashes or generated metadata. Boundary/list changes and source updates use their separate commands.
5. Use `in_progress` for unfinished discussion and provide a next discussion point. Use `refined` only after the discussion has been confirmed, with no tentative items, open questions or next discussion point. `refined` records discussion progress, not formal readiness or execution permission.
6. Before a write, summarize its target files, operation and verification along with the content being confirmed. User-requested mid-discussion saving preserves undecided content as undecided; it does not require completing the TASK first. Do not save on every turn or automatically impose a token threshold.
7. Verify the save result and read back the committed index and current draft. Report the save revision and resume command, then stop at the checkpoint. New-session confirmation checks progress without asking the user to repeat unchanged decisions.
