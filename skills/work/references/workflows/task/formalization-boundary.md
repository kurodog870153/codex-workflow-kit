# Formalization boundary

Before a confirmed addition, split, merge or boundary edit, run `task prepare --expected-revision <revision> --input-file <request-path> --requirement-id <requirement-id> --user-config-root <user-config-root>` with confirmed skill roots. Supply semantic `upsert`, `remove_task_ids`, `current_task` and a non-empty `reason`; reference existing boundaries by `existing_task_id` and new boundaries by one-based `upsert_position`. The CLI allocates IDs above active and retired IDs, preserves unchanged selections and checks dependencies. Source replacement uses the complete source-confirmation request described in read-and-verify.

Review the complete prepare result, affected TASKs and discussions, then save that result with the same requirement, config root and skill roots. Prepared candidates already carry their revision, so omit `--expected-revision` when saving. Preparation writes nothing; save rechecks the fixed snapshot and preserves unaffected history. Repeat the identical approved save after an interruption.

1. A refined discussion's `task_candidate` requires `acceptance_ids`, TASK-specific `acceptance_criteria`, `steps` and `validations`, plus relevant files, commands, decisions, inputs, risks or operations. Responsibilities use stable main IDs such as `ACCEPTANCE-001`; technical criteria use IDs owned by the selected TASK, such as `TASK-001-ACCEPTANCE-001`, and non-empty `criterion` text. Every main criterion needs a responsible TASK, and every responsibility and technical criterion needs VAL coverage. Notes alone are insufficient.
2. Executable records use lowercase local `key` values; the CLI allocates their formal STEP／CMD／VAL／OP IDs. STEP references use `{kind, key}`, VAL uses `command_keys` and stable `acceptance_ids`, OP uses `validation_key` and optional `command_key`, and `task_output` inputs use `dependency_position` and `file_key`. Do not supply duplicate identity, title, goal, skill, dependency or selection metadata inside the candidate. Review retained candidates after boundary changes before reconfirming discussions.
3. Pass document metadata (`title`, `summary`, optional `execution_defaults` and shared `decisions`) to `task preview --input-file <request-path> --requirement-id <requirement-id> --expected-revision <index-revision> --user-config-root <user-config-root>` with confirmed skill roots. The read-only command loads all active refined candidates, checks one complete Source snapshot and TASK-owned selections, and validates the complete formal collection. Review returned `contract` and `execution_index`; all initial acceptance progress is `pending` without evidence.
4. Obtain explicit approval tied to `approval_sha256`. Its single fingerprint binds the saved planning snapshot and exact canonical paths and bytes of TASK index, every item and initial Execution. After approval, run `task apply` with identical metadata and arguments plus `--approved-sha256 <approved-fingerprint>`. Reassembly and source verification occur before exclusive creation. A hash identifies unchanged content; user authorization remains required.
5. Changed Source bytes, unresolved discussion, missing fields or approval mismatch stop creation. Existing formal TASK files are not overwritten. Recover interrupted creation only with the same approved metadata and fingerprint; exact matching files are preserved and missing files restored. Conflicting bytes stop recovery. These operations preserve Source snapshot bytes and historical discussion records.
6. Formal output is `outputs/work/tasks/<requirement-id>/index.json` with referenced `tasks/TASK-NNN.json` items and `outputs/work/executions/<requirement-id>/index.json`. Use `task validate --path <task-index-path> --user-config-root <user-config-root>` with confirmed skill roots to independently verify the formal collection and Source. Initial creation uses preview, apply and recover; changes to existing formal TASK use `$work revise` and Specification. Formal approval does not authorize execution.
