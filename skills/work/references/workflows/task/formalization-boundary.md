# Formalization boundary


Before a confirmed list addition, split, merge or boundary edit, run `task prepare --expected-revision <revision> --input-file <request-path> --requirement-id <requirement-id> --plan-path <plan-path> --user-config-root <user-config-root>` with confirmed skill roots. The semantic request uses `upsert`, `remove_task_ids`, `current_task` and a non-empty `reason`; existing boundaries use `existing_task_id`, new boundaries use one-based `upsert_position`. The CLI allocates new IDs above active and retired IDs, preserves unchanged selections and validates dependencies. Source selection changes use the source request form of `task prepare → save`.

The prepare result contains the complete candidate, affected TASK IDs and changed discussions. Review the effects, then pass the complete prepare result to `task save --input-file <candidate-path>` with the same requirement, Plan path, config root and skill roots. The candidate already carries the expected revision; do not pass `--expected-revision` to `task save` for a prepared list or source candidate. Preparation writes nothing; save rechecks live sources and preserves unaffected history. Repeat the identical save request after an interrupted transaction.

1. Store only semantic TASK content in the optional `task_candidate` field: required `steps` and `validations`, with relevant `files`, `commands`, `decisions`, `inputs`, `risks` or `operations`. Each item has a lowercase local `key`, never a formal ID. STEP `references` use `{kind, key}` for a TASK-local group; VAL uses `command_keys` and one-based `acceptance_positions`; OP uses `validation_key` and optional `command_key`; a `task_output` input uses `dependency_position` and `file_key`. The Work CLI allocates all formal IDs and resolves references from the current Plan and TASK boundaries. Do not include direct ID references, ID, title, goal, skill, dependencies, instruction selection or traceability. Before assembly, every active discussion must be `refined` and contain this object. Notes alone are insufficient. After list changes, review the retained candidate before reconfirming the discussion. The initial assembly links each TASK to all Plan goals, deliverables and acceptance criteria; review these broad traceability links before formal approval.
2. Pass a request file containing document metadata (`title`, `summary`, optional `execution_defaults` and shared `decisions`) to `<work-cli> task preview --input-file "<request-path>" --requirement-id <requirement-id> --expected-revision <index-revision> --plan-path "<plan-path>" --user-config-root "<user-config-root>"` with every Plan `--skill-root`. This read-only command derives paths and source data from the Plan, loads all active structured candidates, and validates the complete initial contract. Review the returned contract's outcomes, file operations, commands and validations with the user; obtain explicit formal approval tied to `approval_sha256`. Do not repeat the full JSON on every discussion turn.
3. After approval, use `task apply` with the identical metadata and arguments plus `--approved-sha256 <approved-fingerprint>`. It reassembles and revalidates before creating the formal TASK collection and execution index; the fingerprint binds both the planning snapshot and canonical logical contract. A hash is evidence of unchanged content, not authorization by itself. Changed sources, unresolved discussion, missing fields or fingerprint mismatch stop creation. An existing formal TASK is not overwritten. Partial formal creation continues to use the separately authorized `task recover` procedure with the identical approved assembled contract.
4. Formal output uses `outputs/work/tasks/<requirement-id>/index.json` plus referenced `tasks/TASK-NNN.json` items. Initial formalization uses `task preview → apply → recover`; later changes to an existing formal collection use `$work revise` and Specification.
