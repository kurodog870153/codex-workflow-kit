# Formalization boundary

1. Discussion plans retain TASK responsibilities, stable main acceptance IDs, TASK-owned technical criteria, direct inputs/files/risks/steps/commands/operations/validations and independent confirmed instruction selections. Executable records use lowercase local keys; deterministic generation allocates formal STEP/CMD/VAL/OP IDs. Dependencies and coverage must be complete and valid.
2. Block formal preview when any required decision is unresolved, planning is missing, Source/instructions drift, dependencies conflict or semantic consistency review is stale. Confirmed decisions alone do not imply complete executable planning. Return to the same Session for discussion and review.
3. Run `task preview --input-file <work-discussion-request.json> --user-config-root <user-config-root>` with kind `preview` and metadata containing title, summary and optional execution_defaults. The read-only result shows actual target paths and complete canonical TASK index, every item and initial Execution bytes, with initial acceptance pending and no fabricated evidence.
4. Obtain explicit approval of the complete preview, bound to `approval_sha256`. Use kind `apply` with exact expected_revision, session_sha256, identical metadata, approved_sha256 and non-empty publication_evidence. Run `task apply` with that request. Approval binds Session/source/content fingerprints and every canonical target path/byte; changed metadata at the same revision also invalidates it.
5. Recompute and verify under the Session/publication locks before creation. Existing formal targets are not overwritten. Recover partial creation only with kind `recover-publication` through `task recover`, identical metadata and exact approval/evidence. Matching bytes are preserved; conflicts stop recovery.
6. Formal output remains the Task index and referenced `tasks/TASK-NNN.json` items plus initial Execution index. Trace binds Session path/revision/content SHA and stable decision IDs/versions to each TASK. Formal validation does not require later Session content to stay unchanged. Use `task validate --path <task-index-path> --user-config-root <user-config-root>` independently; later formal changes use Revise/Specification. Formal approval does not authorize Execute.
7. A nonempty narrative review alone is insufficient: every new publication requires current structured granularity review. Missing, stale, split_required, needs_confirmation or infeasible plans must return to Discussion. Indivisible multi-file outcomes may remain one Task with explicit rationale; no count threshold applies. Existing immutable revisions remain unchanged and must be re-reviewed in a new revision before new publication.
8. Every unordered shared file access needs a decision. Only confirmed modify/modify independence can waive ordering, using exact sorted Task pair, portable path, both actions and both current planning fingerprints in review.file_independence. Create/move and read/write lifecycle conflicts require proper DAG ancestry; shared read/read does not. The validator reads the immutable traced review revision and refuses missing, stale or mismatched evidence without adding an edge.
