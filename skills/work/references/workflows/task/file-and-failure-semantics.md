# File and failure semantics

1. Planning uses `outputs/work/tasks/<requirement-id>/drafts/index.json`. Each `draft_ref` records `save_revision`, draft `revision` and `sha256`; its historical file is `history/<save_revision>/<TASK-ID>.json`. The saved context binds one complete Source snapshot plus independent TASK decisions and selections.
2. Every save exclusively reserves `history/<index-revision>/`, writes and verifies the complete index and changed drafts, then atomically switches the effective index. Unchanged drafts retain earlier references. Root-level `<TASK-ID>.json` files are display copies only. Source replacement confirmation uses the same transaction's `source-update.json`; it does not modify earlier snapshots or history.
3. A successful save with `mirror_status: stale` remains committed despite an outdated display copy; report it and use historical reads. `superseded` means a newer index was observed; read current progress before another write.
4. Inspect every nonzero exit. For a stale revision, obtain fresh status and review. For interrupted initialization, discussion, boundary or source saving, resubmit the identical approved `task save` request with its original arguments. The façade rechecks history and Source and returns recovered or already completed as appropriate. Prepared candidates carry their revision, so omit `--expected-revision`; discussion saves retain that explicit option. Do not delete history, skip revisions or overwrite fingerprints.
5. For addition, split or merge, confirm boundaries, responsibility coverage, dependencies and TASK-owned selections; prepare, review the complete result and save it. The transaction preserves retired IDs and unaffected references and marks affected discussions for review. Source replacement requires complete requirement coverage and the explicit per-TASK confirmation described in read-and-verify.
6. Formal creation uses one approved set of TASK index, referenced items and initial Execution bytes. `task apply` reassembles from the fixed Source and saved discussions and rejects changed content, wrong approval or existing formal targets. For partial creation, use `task recover` with identical metadata, arguments and approval; conflicting existing bytes stop recovery. Repeated recovery may return `already_completed`. Recovery never grants permission to execute TASK commands.
