# Read and verify

1. Read the requirement's committed Session first with `discussion read` or `discussion status`, using a strict `work-discussion-request` whose command kind matches the CLI operation. All Discussion commands accept `--input-file`, `--user-config-root` and confirmed optional `--skill-root` values. The request carries requirement identity; old Task status/prepare/save options are not accepted.
2. Current `session.json` and its corresponding immutable history must agree. A partial uncommitted history is not the newest Session. Show the verified identity, revision, decision counts, current question and necessary dependencies before continuing. Restore the saved numbered option mapping without replaying confirmed choices.
3. Validate original Source bytes and Task-owned hierarchy, skill and instruction selections before relying on source-dependent decisions or generating formal TASK. Reading Session preserves historical evidence even when formal sources have drifted; it grants no current readiness.
4. Keep Source snapshots immutable. A confirmed context update increments context revision and marks affected decisions/plans for review; reconfirm their semantic consistency and current instruction bindings before preview. Existing formal Source changes use the complete Specification source-confirmation contract and its unchanged acceptance review rules.
5. Do not infer selections from notes, refresh external requirements, merge unrelated historical snapshots or silently convert retired outputs. Load only the selected TASK's applicable instructions and one assigned skill; use other TASKs for necessary dependency/boundary summaries.
