# Read and verify

Run `<work-cli> task status --requirement-id <requirement-id> --user-config-root <user-config-root>` with confirmed `--skill-root` values first; add `--task-id <task-id>` for an explicit choice. Status verifies the committed index and selected historical discussion, reports boundaries and `next_action`, and checks the fixed Source and TASK-owned skill and instruction selections. Review drift before relying on saved decisions.

1. The CLI follows `draft_ref` for the selected discussion. The root-level TASK display copy is not resume evidence. Read the index and selected discussion rather than every TASK or transcript.
2. Validate the bound immutable snapshot using `source validate --requirement-id <requirement-id> --source-id <source-id>` and the configured Source root when needed. Compare its manifest and exact requirement bytes with the saved `source.snapshot`; `task status` also checks the complete source context and confirmed selections. Storage integrity does not itself authorize a write.
3. Confirm the selected TASK's instruction paths and references explicitly. An ambiguous selection or changed instruction fingerprint requires review through `task prepare → save`; never derive a selection from notes or rewrite historical evidence.
4. Load only the selected TASK's applicable instructions and its one assigned full skill. Use other TASKs only for necessary boundary and dependency summaries. Assigned skill IDs must belong to the independently confirmed TASK skill selection.
5. Replace a source only with one complete effective requirement snapshot, keeping the earlier snapshot immutable. Confirm a source request containing `source`, non-empty `reason`, exact affected-TASK `selections`, and `source_confirmation`. The confirmation binds `previous_planning_sha256`, `new_source_sha256` and `requirement_sha256`, sets `complete_requirement_review: true`, and lists `retained_acceptance_ids`, `removed_acceptance` entries with explicit reasons, and `added_acceptance_ids`.
6. Supply `task_reviews` for exactly every affected TASK. Each review records `outcome_decisions`, `technical_decisions`, `boundary`, `acceptance`, `skills`, `hierarchy` and `instructions`. Partial requirement coverage, multiple snapshots, unconfirmed selections or drift after approval stop the update.
7. Run `task prepare --input-file <request-path> --requirement-id <requirement-id> --user-config-root <user-config-root>` with confirmed skill roots. Review the complete candidate and affected discussions, then save that result with the same arguments and without `--expected-revision`. Save rechecks sources and persists confirmation in the existing `history/<revision>/source-update.json`. Repeat the identical approved save after interruption. Reconfirm affected discussions before formalization; preserve old snapshot bytes and history.
