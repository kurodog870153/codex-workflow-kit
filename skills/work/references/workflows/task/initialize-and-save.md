# Initialize and save


For initial planning, use read-only `task prepare --input-file <request-path> --requirement-id <requirement-id> --plan-path <plan-path> --user-config-root <user-config-root>` with confirmed skill roots. Supply semantic `upsert`, empty `remove_task_ids`, explicit `current_task`, and `reason: null`; reference new items by one-based `upsert_position`. Review the complete `work-task-draft-prepare/v1` result, then pass that result as the input file to `task save` with the same requirement, Plan path, config root and skill roots. The save rechecks sources; repeat the identical request after an interruption.

1. The first `task save` creates the planning index from the approved prepare result. Do not author a full index, assign TASK IDs or use a separate initialization command.
2. The index stores requirement ID, source fingerprints, current TASK and boundaries (`id`, `title`, `goal`, `scope`, `skill_id`, direct `dependencies`, planning `status`, `boundary_revision`, `instructions_sha256`). Include each confirmed `instruction_selection` as `{"selected_paths": [...], "references": [...]}` on its TASK entry, including empty arrays for explicitly confirmed general-only without references. The index is the single structured source; do not duplicate this field in discussion drafts. Existing entries without it remain readable. The first authorized discussion save with an explicit selection verifies its fingerprint and records it without changing the boundary revision. Source updates record their revalidated selections; list updates preserve selections of existing TASKs. Never edit old history to add the field.
3. Keep each discussion as `work-task-draft/v1`: save detailed `notes`, `confirmed_decisions` with `statement` and `rationale`, `tentative`, `open_questions`, and `next_discussion_point`. Preserve concrete file, command, validation and instruction-selection details needed later; do not substitute a vague summary or put unconfirmed proposals among confirmed decisions.
4. Save one complete discussion with `task save --input-file <request-path> --requirement-id <requirement-id> --task-id <task-id> --expected-revision <revision> --plan-path <plan-path> --user-config-root <user-config-root>` and confirmed skill roots. The request contains status, notes, confirmed decisions, tentative items, open questions, next discussion point and optional semantic `task_candidate`. Send the full selected discussion, not a patch; the CLI rechecks sources and derives metadata. Use `task prepare → save` for boundary and source changes.
5. Use `in_progress` for unfinished discussion and provide a next discussion point. Use `refined` only after the discussion has been confirmed, with no tentative items, open questions or next discussion point. `refined` records discussion progress, not formal readiness or execution permission.
6. Before a write, summarize its target files, operation and verification along with the content being confirmed. User-requested mid-discussion saving preserves undecided content as undecided; it does not require completing the TASK first. Do not save on every turn or automatically impose a token threshold.
7. Verify the save result with `task status` using the same source arguments; report the revision and selected TASK. A new session can resume from the committed history without repeating unchanged decisions.
