# Initialize and save

For initial planning, use read-only `task prepare --input-file <request-path> --requirement-id <requirement-id> --user-config-root <user-config-root>` with confirmed skill roots. The semantic request contains `source`, `upsert`, empty `remove_task_ids`, explicit `current_task`, and `reason: null`. The `source` context contains one complete immutable `snapshot`, portable `artifacts` paths, and independently confirmed TASK-owned `hierarchy_selection`, `skill_selection` and main `acceptance_criteria`. Snapshot bytes preserve the original requirement; selections and acceptance decisions belong to TASK. Reference new boundaries by one-based `upsert_position`.

1. Review the complete `work-task-draft-prepare` result, then pass that result to `task save --input-file <candidate-path> --requirement-id <requirement-id> --user-config-root <user-config-root>` with the same skill roots. The candidate carries its expected revision; omit `--expected-revision` for a prepared candidate. Save rechecks the exact Source and confirmed selections. Resubmit the identical approved request after an interruption.
2. The first save creates `outputs/work/tasks/<requirement-id>/drafts/index.json`. Let the CLI allocate TASK IDs. The index stores boundaries, dependencies, current TASK, source context, stable main acceptance IDs and instruction fingerprints. Every boundary has an explicitly confirmed `instruction_selection` with `selected_paths` and `references`; empty arrays mean confirmed general-only without references. Discussion drafts do not duplicate the selection. Never edit historical files to repair a selection.
3. Keep discussions as `work-task-draft`: preserve detailed `notes`, confirmed decisions with `statement` and `rationale`, tentative proposals, open questions and the next discussion point. Distinguish outcome decisions from technical decisions and retain the concrete evidence needed for formalization.
4. Save one complete discussion using `task save --input-file <request-path> --requirement-id <requirement-id> --task-id <task-id> --expected-revision <revision> --user-config-root <user-config-root>` with confirmed skill roots. Supply status, notes, confirmed decisions, tentative items, open questions, next discussion point and optional semantic `task_candidate`. Send the complete discussion rather than a patch; metadata is derived by the CLI. Boundary and source changes use `task prepare → save`.
5. Use `in_progress` with a next discussion point while decisions remain unresolved. Use `refined` only after confirmation, with no tentative items, open questions or next discussion point, and a complete candidate including TASK responsibilities, its technical acceptance criteria, steps and validations. Refinement records discussion progress; formal approval and execution authorization are separate decisions.
6. Before saving, describe the target files, operation, content and verification covered by the user's authorization. A requested checkpoint may retain undecided content as undecided. Do not force completion or save automatically on every turn.
7. Verify the save using `task status` with the same requirement, user config root and skill roots. Report the saved revision and selected TASK. Resume from committed historical references without repeating unchanged decisions.
