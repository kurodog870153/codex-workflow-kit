# Use deterministic handoffs

Apply the shared handoff procedure for unchanged transport, source verification and authorization boundaries.

1. For `execute_to_task`, save received JSON unchanged and run `handoff verify-execute-to-task --input-file <request-path> --task-path <confirmed-task-path> --task-id <confirmed-task-id> --user-config-root <user-config-root>` with all confirmed skill roots and exactly one independently selected `--attempt-id <attempt-id>` or `--preflight`. Require `work-handoff-source-validation/v1` with `status: valid`. Verification checks formal TASK, its fixed Source, current Execution and latest Attempt; closed returns also compare exact Attempt bytes. Reject drift without rewriting received fields.
2. After formalization and explicit selection of one TASK, supply only `{"summary": <handoff-summary>}` to `handoff build-task-to-execute --input-file <request-path> --task-path <task-path> --task-id <task-id> --user-config-root <user-config-root>` with confirmed skill roots. The read-only builder validates the complete collection and fixed Source, derives artifact paths and fingerprints, and rechecks sources. It does not approve preflight, worktree changes or Attempt creation.
3. For confirmed changes to an existing formal specification, use `$work revise` through the parent. An unsaved discussion may use `handoff build-discussion --input-file <request-path>` with `work-discussion-handoff-request/v1` and either legal Task/Execute direction. Its `source_validation: not_checked` result cannot replace formal verification or authorize publication.
