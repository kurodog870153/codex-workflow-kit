# Reviewed TASK Repair

Load this procedure only after the user has reviewed the shared TASK diagnostic report and decided a repair direction. The parent retains the original continuation point and routes the repair to the artifact editor or its existing fallback. Diagnosis, repair-direction approval and approval to write the concrete candidate are separate steps.

## Prepare the request

1. Preserve the original bytes, confirmed requirement ID, all three artifact paths, diagnostic issues and the user's decisions. For invalid encoding or ambiguous JSON, ask for the intended interpretation; never try alternate encodings or discard duplicate/unknown values silently. The repair record preserves original bytes in base64, including undecodable input.
2. Prepare one UTF-8 JSON request file with schema `work-task-repair-request/v1` and exactly `schema`, `stage`, `requirement_id`, `artifacts`, `expected`, `decisions` and `task`. `artifacts` contains normalized project-relative `plan`, `task`, `execution` paths. `expected` contains original raw-byte `plan_sha256`, `task_sha256`, `index_sha256`. `decisions` is a nonempty array of `{"location": "/JSON/pointer", "decision": "The user's confirmed interpretation and evidence"}`; use `/` for a whole-document interpretation. `task` is the complete explicitly reviewed candidate object, including retained unknown fields and unresolved omissions.
3. Choose `stage=format` to repair encoding, JSON syntax, field representation or a reviewed legacy conversion without requiring missing semantic decisions. The candidate must be a canonical UTF-8 JSON object with the current schema and confirmed requirement/artifact identity. Missing requirements, acceptance and technical decisions remain missing; do not insert nulls, placeholder prose, empty invented records or readiness claims. Unknown retained fields remain diagnostic issues. The CLI only orders/serializes the supplied values and does not infer repairs. It leaves Plan and index bytes unchanged in this stage.
4. After independently possible format repair is written and diagnosed again, route remaining requirement/acceptance decisions to Plan and technical decisions to Task through the parent. Retain prior answers. An incomplete structure or full contract continues to block normal use even when format passes. Independent progress save/restore remains available.
5. Choose `stage=complete` only after the required decisions are settled and the candidate passes the existing full TASK contract against the unchanged Plan and current sources. The CLI derives index bindings and preserves existing TASK IDs. It never accepts a caller-supplied index or changes historical Attempt/Correction files. Unknown or changed TASK meaning conservatively affects every existing TASK; changed non-pending rows become pending_retry when they have an Attempt, otherwise blocked. Changes affecting cancelled TASKs require a separate lifecycle decision. Review all resulting index changes. Repairs do not rename requirements, add/remove TASK identities or revise Plan; use the existing coordinated specification workflow for a subsequent confirmed scope revision.
6. Existing Plan and index files must be readable, and index state must validate before a preview is possible. Locks, active TASKs/Attempts, a busy OS writer or incomplete transactions prohibit repair preview and writes. Return diagnostics; never close or recover execution automatically. Source Plan or instruction drift may remain visible during format repair; complete repair cannot bypass current source checks or treat refreshing hashes alone as content review.

## Review, approve and publish

1. Run `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>" task repair-validate --input-file "<request-path>" --user-config-root "<user-config-root>"`, including confirmed skill roots. This is read-only and creates no mutex or journal. Parse the stdout envelope on success and failure.
2. Review response `data` (`work-task-repair/v1`): the original raw-byte evidence, full before/after text and unified diffs for TASK/index, affected TASKs, retained decisions and candidate diagnostics. Undecodable original text is displayed as byte escapes, not guessed text; base64 retains exact originals. Check `format_status`, `structure_status`, `contract_status` and `normal_use_allowed` separately. Preview success means the selected repair stage is reviewable, not that the TASK is executable.
3. Present the complete candidate set, exact commands, validation results, remaining decisions and risks. Obtain separate write approval bound to `approved_sha256`. That fingerprint includes decisions, original and candidate bytes, history and diagnostic evidence. Any change requires a new preview and approval.
4. Run `task repair --input-file "<same-request-path>" --user-config-root "<user-config-root>" --approved-sha256 "<reviewed-fingerprint>"` with the same global project root and skill-root arguments. The CLI rechecks sources and blockers under the shared writer mutex, records exact originals/candidates, replaces TASK and any derived index, and repeats diagnosis before writing the completion marker. No shell pipelines, redirection, chaining or platform-specific environment expansion are needed.
5. The transaction journal is `<execution-dir>/.work-task-repair-<fingerprint>.json`; its matching `.done` file contains the journal's SHA-256. Incomplete repair journals block normal Work use and other specification transactions. Multi-file publication is recoverable and guarded, not a filesystem-wide atomic rename. Preserve journals, backups and any partial temporary files.
6. A `repaired` result only confirms the reviewed stage was installed. After format repair, discuss unresolved content and prepare another separately approved repair if needed. After complete repair, reload the sources and perform normal Execute preflight, including file-state checks and execution approval. The repair transaction does not execute any TASK record.

## Authorized recovery

1. On interruption, preserve the original request, approval fingerprint, journal and current artifacts. Do not retry apply or roll back automatically. Report `task_repair_interrupted`, the record path and `recovery_required`.
2. After separate recovery authorization, run `task repair-recover` with the identical request and fingerprint. Recovery accepts only the exact approved before/after artifact bytes, preserves historical execution, rejects changed source/instruction evidence and completes only matching partial journal/temp/marker prefixes. Unrelated incomplete transactions remain blockers.
3. Recovery returns `recovered` or `already_completed`; conflicting bytes remain untouched. Return the resulting diagnostics to the originating role at the saved continuation point. Recovery approval does not authorize new repair decisions or execution.
