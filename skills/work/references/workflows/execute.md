# Execute Workflow

Before relying on an existing formal TASK, apply [the shared TASK diagnostic gate](../instruction-loading.md#validate-before-relying-on-a-formal-task). Inspect raw content only for diagnosis until validation passes; preserve independent discussion progress and initial-artifact exceptions.

Use this workflow only after the formal target TASK and its single external skill selection have been validated. In this file, `<work-cli>` means `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>"`.

## Handle invalid related artifacts before execution

1. Normal execution still requires a validated current formal TASK. When the source Plan, TASK collection, execution index, or their bindings instead require reconstruction, stop eligibility and follow [AI cross-file migration](../instruction-loading.md#ai-cross-file-migration); the invalid originals are evidence and do not need to pass current validators first.
2. Use current Execute rules and immutable Attempt and Correction history to constrain complete current `v1` candidates. Do not migrate through Python, reinterpret incompatible layouts merely because their schema IDs match, or rewrite historical execution evidence.
3. Ask through the parent only when preserved execution evidence and current rules permit more than one lifecycle or specification meaning. Derived execution-index structure, fingerprints, and uniquely determined status bindings require no semantic decision.
4. Keep every affected execution-index candidate in the same atomic set as its Plan and TASK candidates. Migration discussion, candidate validation, or approval does not authorize an Attempt, execution record, recovery, or independent file write.

## Load only the target skill

1. Use only the target TASK `skill_id`. `null` means base-only and loads no external skill.
2. Resolve a non-null ID only from the source Plan `skill_selection`. Do not scan, recommend, or combine other skills.
3. Require Execute mode support, available dependencies, the same root identity, and unchanged summary and bundle fingerprints.
4. Pass the same `--skill-root` values to every Execute CLI command. Any missing root or drift is a hard stop.

## Identify the execution target

1. Loading Execute instructions alone does not execute or authorize a TASK.
2. Require the user to identify one formal TASK collection entry point and one `TASK-*` from that specification before eligibility checks. Do not select either on the user's behalf. The loader validates the collection and exposes the selected dependency closure required by the operation.
3. Use the default TASK collection entry path `outputs/work/tasks/<requirement-id>/index.json` unless the user explicitly supplies and confirms a permitted project-relative collection entry path. The entry filename must be `index.json`; single-file `task.json` artifacts are unsupported.
4. When Plan, TASK, or execution uses a non-default path, require the same requirement ID and all three confirmed project-relative paths. Never infer one path from another.
5. After the target is complete, perform only authorized read-only eligibility checks. Obtain every required authorization before changing state, modifying files, running side-effecting commands, or performing external operations.

## Run deterministic read-only eligibility checks

1. Run `<work-cli> execute preflight --task-path "<task-path>" --execution-dir "<execution-dir>" --task-id <task-id> [--skill-root <scope:locator=path> ...] [--confirmed-input <TASK-ID>/<INPUT-ID> ...]`.
2. Pass `--confirmed-input` once for each current-TASK `user_provided` or `external` input only after the user or applicable external evidence confirms it. Pass IDs only, never secret values.
3. Require `work-execute-preflight/v1` with `eligibility: passed`. Treat every nonzero exit code as a hard stop.
4. Require the returned `hierarchy_selection_sha256` to match the formal TASK and index, and use the returned TASK, Task instruction, Execute instruction, input, and file-readiness results without recomputing them in the model. Preflight is read-only and does not authorize or create an Attempt, lock, state transition, record, or artifact change.
5. Run the same arguments through `<work-cli> execute worktree`. Treat `path_classification` only as path-overlap evidence; `target_task`, `completed_dependency`, and `unrelated` never prove ownership.
6. When `review_status` is `required`, explain every returned change using the approved TASK, a valid Attempt or Correction, or known prior results. Stop when any path or content may belong to the user or cannot be explained. The command excludes only the current execution directory and never modifies Git.

## Request coordinated revision

1. For confirmed changes to existing formal artifacts, follow [the shared coordinated revision procedure](../instruction-loading.md#coordinated-formal-artifact-revision). Initial creation and cross-session handoffs retain the procedures in this workflow.

## Apply one Attempt authorization boundary

1. Before starting an Attempt, present one complete authorization summary covering the target TASK, files, formal CMDs, OPs and VALs, expected side effects, external operations, risks, validation and normal Attempt closure. Bind authorization to that exact reviewed scope and the current worktree snapshot. Platform or sandbox permission remains independently required when the runtime requests it; an Attempt authorization never substitutes for platform permission.
2. After the Attempt starts, do not ask again before `record-begin`, execution, `record-finish`, routine validation or normal `attempt-close` when the exact operation and effects remain inside that authorization. These state transitions still perform every source, lock, fingerprint and recovery check; absence of another conversational confirmation is not permission to widen their scope.
3. Stop and obtain a new decision before any unlisted file, command capability, external operation or side effect; any source or worktree drift that invalidates the reviewed scope; any uncertain result; any retry not already fixed by the TASK and authorization; or any recovery. A new decision may authorize only the reviewed addition or direct a specification return; it does not silently replace the original TASK.
4. Classify an execution-time insufficiency as an execution deviation only when the requirement, acceptance criteria, deliverables, safety boundary and external side-effect boundary remain unchanged. Equivalent command corrections, necessary commands or validations, skipped inapplicable records and implementation adjustments may use this class after the user reviews their exact effects. A change to any of those semantic boundaries is a specification defect and must use the coordinated revision or handoff path.
5. Until the execution-deviation contracts and transactions are implemented, the classification in item 4 is a decision boundary only: preserve the proposed deviation and the user's decision in discussion or approved progress, but do not invent unsupported Attempt fields, records or CLI behavior. Continue only through capabilities already represented by the current formal TASK and contracts; otherwise close or refrain from starting the Attempt and return for specification revision.
6. At Attempt closure, summarize every accepted deviation and ask once whether each should be incorporated into Plan/TASK, selectively incorporated, or retained only as execution evidence. Save the AI-produced complete candidates with that choice and run `task reconciliation-preview`; when publication is selected, bind approval to its fingerprint and use `task reconciliation-apply`. This separate process never rewrites the closed Attempt. An interrupted nested migration requires separately authorized `task migration-recover` with the migration request and fingerprint returned by the preview.

## Use deterministic handoffs

Apply [the shared handoff procedure](../instruction-loading.md#shared-handoff-procedure) for transport, source verification, legacy evidence and authorization boundaries.

1. Before using `task_to_execute`, save the received JSON unchanged as the request file and invoke `<work-cli> handoff verify-task-to-execute --input-file "<request-path>" --task-path "<confirmed-task-path>" --task-id <confirmed-task-id> --user-config-root "<user-config-root>"` with every confirmed `--skill-root`. Use the explicitly selected formal TASK path and TASK ID, not targets chosen solely from the incoming handoff. Require `work-handoff-source-validation/v1` with `status: valid`. The command validates the current TASK and source Plan, rejects incomplete specification transactions, and compares requirement ID, artifact paths, specification and TASK IDs, task-specific instruction fingerprint, skill ID and source fingerprints. Reject stale or mismatched handoffs without rewriting their fields. This verifies source identity, not semantic approval; it does not replace preflight, worktree review or authorization to start an Attempt.
2. For a specification defect requiring a cross-session handoff with an existing stopped or blocked Attempt, save a JSON request file containing only `summary`, `reason` (the specification defect explanation), `confirmed_approach`, `requested_changes`, `preserve`, `affected_ids`, and `validation_requirements` and invoke `<work-cli> handoff build-execute-to-task --input-file "<request-path>" --task-path "<task-path>" --task-id <TASK-ID> --attempt-id <ATTEMPT-ID> --user-config-root "<user-config-root>"` with every confirmed `--skill-root`; use `build-execute-to-plan` when returning to Plan. The command validates the latest closed Attempt against TASK, Plan, index, and current instruction/skill fingerprints, and derives the machine fields. A blocked Attempt's recorded closing reason remains unchanged; `reason` explains why the requested return concerns a specification defect. Require success before relaying the result. Confirmed same-session revisions use the internal editor above.
3. For a cross-session specification handoff before any Attempt exists for the target TASK, use the same semantic request and command with `--preflight` instead of `--attempt-id`. The command requires a valid Plan, TASK, and index, an initial `pending` TASK, no lock or transaction residue, and an absent or empty target TASK execution directory. It derives `attempt: {"status": "not_created"}` and `phase: preflight`; never supply those fields yourself. It validates source identity without requiring inputs, dependencies, or file readiness to pass, and does not classify a preflight failure as a specification defect automatically. `reason` must explain that judgment. Existing Attempt history must use the closed-Attempt path. A successful handoff is not a successful eligibility check or permission to resume execution.

## Use the canonical Attempt contract

1. Before proposing an Attempt write, save the proposed pure `work-attempt/v1` JSON as the request file and invoke `<work-cli> attempt validate --input-file "<request-path>"` and require `work-attempt-validation/v1` with `result: valid`.
2. Use `<work-cli> attempt render --input-file "<request-path>"` to canonicalize field order. Validate an existing canonical document with `<work-cli> attempt validate --path "<attempt-path>"`.
3. These commands are read-only contract operations. They do not create an Attempt, acquire a lock, update the index, execute a record, or authorize state changes.

## Start an Attempt transaction

1. Require the user to review the complete `execute worktree` result and retain `snapshot_sha256`. The hash is not approval by itself.
2. After the complete Attempt authorization above, save pure `work-attempt-start-request/v1` JSON containing `worktree_snapshot_sha256` and a complete `work-attempt-authorization/v1` manifest as the request file and invoke `<work-cli> execute attempt-start --input-file "<request-path>"` with the same preflight arguments. The manifest contains the exact commands, validations, modifiable files, working directories, external operations and fully specified allowed deviation actions, the fixed reapproval conditions, and concise actual authorization evidence. For `pending_retry`, also provide the latest source Attempt and only carried record IDs whose current evidence was explicitly confirmed.
3. The command rechecks preflight and Git snapshot, rejects manifest entries that do not exactly match or narrow the current TASK, derives the authorization fingerprint, canonical Attempt identity, `skill_id`, hierarchy-selection, skill-selection and instruction fingerprints, and local-offset time, then installs the lock and creates the Attempt.
4. `recovery_required: true` is a hard stop. Summarize the transaction stage and obtain separate authorization before running `<work-cli> execute recover-attempt-start --input-file "<request-path>"` with identical paths, inputs, and request. Recovery advances only an exactly matching state and never rolls back, deletes, unlocks, or resolves conflicts.

## Reserve one execution record

1. Before executing one formal CMD, OP, or VAL, verify that its exact base ID, action and effects remain inside the current Attempt authorization, then run `<work-cli> execute record-begin --task-path "<task-path>" --execution-dir "<execution-dir>" --task-id <task-id> --record-id <base-record-id>`. Do not request another confirmation solely for this reservation.
2. Pass only the formal base ID such as `CMD-001`. The command validates the active Attempt, TASK, and current instruction fingerprints, derives any retry suffix, and adds the exact `record_id` to the execution lock.
3. Require `work-record-begin/v1` with `lock_status: record_reserved` before performing the authorized record. The command does not execute or append the CMD, OP, or VAL.
4. `recovery_required: true` is a hard stop. Preserve the lock and transaction file; do not retry, execute the record, or modify the index until separately authorized recovery handles it.

## Record an equivalent command correction

1. If a reserved CMD needs an equivalent syntax, quoting, escaping, argument-format, or executable-path correction, apply the execution-deviation boundary above. Obtain a new decision for the exact replacement unless that exact correction was already included in the current Attempt authorization; never treat semantic, side-effect or safety changes as an equivalent correction.
2. Save pure `work-command-correction-request/v1` JSON as the request file and invoke `<work-cli> execute command-correction --input-file "<request-path>"`. Include the reserved `record_id`, canonical `original_command` and `actual_command`, a non-empty reason, and minimal authorization evidence.
3. Require `work-command-correction/v1` with `correction_status: recorded` and `lock_status: record_reserved` before executing the corrected command. The tool verifies the original formal command and stores the correction in the lock; it does not execute the command or decide semantic equivalence.
4. `recovery_required: true` is a hard stop. Preserve the record lock and `.work-command-correction-*.tmp`; do not execute or resubmit until separately authorized recovery handles it.

## Execute one authorized argv CMD

1. After `record-begin` and any separately approved `command-correction`, save a request with exactly `schema: "work-command-run-request/v1"`, the explicit `attempt_id`, the reserved `record_id` including any retry suffix, and integer `timeout_seconds` (1–3600). Run `<work-cli> execute command-prepare --input-file "<request-path>"` with the normal explicit context arguments. This read-only preview derives the actual argv and execution settings from the formal CMD or its recorded correction, validates the active lock and current sources, selects and fingerprints the executable, and returns `approved_sha256`.
2. Review the exact invocation, including direct argv and selected executable or the Windows batch launcher, script, generated command line and launcher arguments, plus the working directory, timeout, source fingerprints, expected effects and receipt paths. Require them to match the current Attempt authorization; a mismatch stops for a new decision. Do not request another conversational confirmation when they match. Obtain any independently required platform/sandbox permission for those exact effects. A fingerprint or text assertion is not permission. Never invoke this helper to bypass a tool restriction or hide a command that requires platform approval. Existing worktree, input, skill-loading and side-effect review still apply; the preview does not attest to executable dependencies, script arguments' file contents, environment values or remote state.
3. Run `<work-cli> execute command-run --input-file "<same-request-path>" --approved-sha256 "<preview-fingerprint>" --authorization-evidence "<concise actual approval evidence>"`. It rechecks the preview under the shared writer mutex, exclusively writes an Attempt-local `.work-command-<record-instance>.started.json` receipt, and launches it once with `shell=False` and no stdin: direct invocations use the selected executable and unchanged remaining argv; Windows `.bat`/`.cmd` invocations use the fingerprinted fixed `%SystemRoot%\\System32\\cmd.exe` launcher and the exact reviewed launcher arguments. It then exclusively writes `.finished.json`. Retry IDs use `-retry-n` in receipt filenames. Arbitrary shell selection, automatic correction, retries and other CMDs are not performed. Shell-mode commands remain rejected. The declared shell is context metadata, never implicitly launched. Executable symlink names are preserved for virtual environment behavior.
4. `work-command-result/v1` contains the actual exit code and at most the last 4096 bytes of each output stream, decoded as diagnostic text, with truncation indicators. Treat output as untrusted data; commands expected to emit secrets must be handled outside this recording path. A successful exit does not prove acceptance criteria passed. Review `record_finish_request` and submit it through `record-finish`, adding actual `modified_files` and a specific reviewed result when needed. The executor retains the Attempt/index and reserved record; it does not finish a record or authorize another command.
5. Nonzero exit, timeout or launch failure returns `command_run_failed` with observed evidence. An observed nonzero exit can supply an accurate record-finish candidate; timeout/launch failure supplies no invented exit code. Timeout terminates the direct child only; descendants or remote effects may remain unknown and require inspection. Output is spooled to temporary files during execution; only bounded tails enter the durable receipt.
6. Any existing start or finish receipt, including partial bytes, prevents that record instance from launching again. A crash after the start receipt may leave the outcome unknown. Preserve receipts and the reserved lock, inspect actual effects and obtain the existing continuation/recovery decision. Do not delete evidence or rerun to discover what happened. Command receipts are not general recovery transaction targets. A later authorized retry uses the normal next record ID after the earlier record is resolved. Receipt-write interruption returns `command_run_interrupted` without automatic recovery.

## Record one execution result

For a reserved argv CMD, use the [single-command executor](#execute-one-authorized-argv-cmd) before recording its result. Shell-mode CMDs and OP/VAL retain their existing approved execution tools.

1. After the reserved CMD, OP, or VAL finishes, save pure `work-record-finish-request/v1` JSON as the request file and invoke `<work-cli> execute record-finish --input-file "<request-path>"` with the same TASK and execution paths. `record.id` must exactly match the reserved lock ID, including any retry suffix. Accurate recording of an authorized operation does not require another confirmation; uncertain or expanded effects stop under the Attempt authorization boundary.
2. Command uses `exit_code` and `result`; operation uses `outcome` and `state`; validation uses `outcome` and `evidence`. Do not repeat command-correction data. Include normalized `modified_files` only when the record changed files.
3. The command validates the formal record and current instruction fingerprints, moves a locked command correction into the command record, atomically appends the canonical Attempt record, updates cumulative modified files and operation outcome, then removes `record_id` and its correction from the lock. It never executes the record or releases the Attempt lock.
4. `recovery_required: true` is a hard stop. Preserve the Attempt, lock, and transaction files; do not resubmit the result or begin another record until separately authorized recovery handles the state.

## Close one Attempt

1. After all authorized records finish, save pure `work-attempt-close-request/v1` JSON as the request file and invoke `<work-cli> execute attempt-close --input-file "<request-path>"` with the same TASK and execution paths without another confirmation when the reviewed normal-completion condition is satisfied. A stopped or blocked outcome, uncertain effects, an unreviewed deviation or any closure outside the authorized condition requires a new decision before close.
2. Use `status: completed` without final details only when every formal VAL has a latest passed result or valid carried evidence. Use `stopped` or `blocked` with an allowed `final_type` and non-empty reason.
3. The command verifies no record remains reserved, checks current instruction fingerprints, derives local-offset end time, writes the canonical closed Attempt first, then atomically synchronizes TASK and overall status while releasing the matching execution lock. It never executes a record.
4. Require `work-attempt-close/v1` with `lock_status: released`. `recovery_required: true` is a hard stop: preserve the closed Attempt, lock, and `.work-attempt-close-*.tmp`; do not repeat close or manually unlock until separately authorized recovery handles it.

## Create an immutable Correction

1. Use a Correction only for a confirmed factual error in a closed Attempt or its index state. Never modify the original Attempt, TASK, implementation, or execution evidence.
2. After separate authorization, save pure `work-correction-create-request/v1` JSON as the request file and invoke `<work-cli> execute correction-create --input-file "<request-path>"`. Provide `target_attempt_id`, `field`, `correct_value`, `reason`, and explicit boolean `invalidates_completion`.
3. The command derives the next Correction ID, local-offset time, and original Attempt instruction fingerprints; installs a Correction lock, exclusively creates canonical `work-correction/v1`, synchronizes `latest_correction` and invalidated completed downstream TASK statuses, then releases the lock.
4. Require `work-correction-create/v1` with `lock_status: released`. `recovery_required: true` is a hard stop; preserve the immutable target, lock, and `.work-correction-*.tmp` files for separately authorized recovery.

## Recover one execution transaction

1. Use `<work-cli> execute recover --input-file "<request-path>"` only after record-begin, command-correction, record-finish, attempt-close, or Correction reports `recovery_required: true` and the user separately authorizes recovery of the observed state. Attempt-start continues to use `recover-attempt-start`.
2. First use the read-only `<work-cli> execute recovery-prepare --input-file "<preparation-path>"` with the normal explicit TASK/execution paths, TASK ID and roots. Its input has exactly `schema: "work-execution-recovery-prepare-request/v1"`, the confirmed `transaction` (`record_begin`, `command_correction`, `record_finish`, `attempt_close` or `correction`) and `attempt_id`. It inventories the complete sorted `.work-*.tmp` set, checks formal identities and preserved canonical documents, and returns `data.request` in the existing `work-execution-recovery-request/v1` format plus lock, status and raw file fingerprints. Save only `data.request` for authorized recovery. No writer mutex file, target, journal or lock is created or modified.
3. Require `work-execution-recovery/v1` with `status: recovered`. The command revalidates formal TASK identity, canonical Attempt, index, original lock fingerprint, and every prepared byte before advancing only the uniquely determined transaction.
4. Any file-set change, byte mismatch, ambiguous state, unsupported attempt-start transaction, or write failure is a hard stop. Preserve all artifacts and locks; never retry automatically, roll back, delete a transaction file, rewrite a closed Attempt, or manually unlock.
5. Preparation is an inventory for review, not approval or proof of a unique recovery target. `recovery_validation: requires_authorized_recover` remains explicit: the existing recovery command reconstructs and verifies the transaction targets after separate authorization. File hashes describe this snapshot; they are not added to the existing recovery request or an approval token. Preparation rejects mixed transactions and empty inventories unless the Attempt/lock show a supported record-finish or attempt-close post-write stage. Reinspect evidence before authorization; external effects and the recovery direction still require human review. Attempt-start continues to use its original request and dedicated recovery procedure.
An authorized Attempt reuses the authorization manifest for matching commands,
validations, external operations, file changes, and allowed deviations. Retries,
recovery, failed or unknown results, and stopped or blocked closure require fresh
authorization evidence. Any scope expansion stops before the operation.
