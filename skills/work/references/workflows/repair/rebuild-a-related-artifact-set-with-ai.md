# Rebuild a related artifact set with AI


1. When a Plan, TASK collection, execution index, or their bindings use an old, malformed, or internally incompatible representation, preserve the original bytes and read the current contracts and workflows before constructing a replacement. The source artifacts do not need to parse or pass any current validator before reconstruction begins; failed validation is evidence about the source, not an input contract for the reconstruction.
2. Rebuild the complete related set directly in the current `v1` formats. Do not create or invoke a Python migration, compatibility adapter, schema-version conversion chain, or intermediate legacy document. A matching schema ID is not proof that two documents have the same representation; when the actual fields or relationships are incompatible, treat the source as a different format and replace it with the representation required by the current contract.
3. Infer only facts uniquely supported by the preserved artifacts, current rules, repository evidence, and confirmed decisions. Formatting, canonical ordering, derived fingerprints, and other mechanically unique corrections do not require a semantic decision. Duplicate values, conflicting identities, missing meaning, or any other evidence that permits more than one materially different current document must stop for one explicit user decision; never select an interpretation, invent a value, or insert placeholder content.
4. Produce complete candidate bytes for every related Plan, TASK index and item, and execution index affected by the reconstruction. Validate only the candidates against the current contracts and cross-file relationships. Historical Attempts and Corrections remain immutable evidence and may constrain the candidates, but are not rewritten as migration output.
5. Treat the candidates as one indivisible change set. Review the complete source evidence, candidate set, cross-file diff, validation results, unresolved decisions, effects, and risks before requesting write approval. If any candidate or relationship is incomplete, keep the whole set unwritten.
6. Save the complete request and run `task migration-preview`. After reviewing its exact diff, current-validator results, relationship results, unresolved items and fingerprint, obtain write approval bound to that fingerprint. Publish only with `task migration-apply --input-file <same-request> --approved-sha256 <fingerprint>`; do not substitute TASK repair, independent writes or an improvised script.
7. Publication stores original and candidate bytes in `<execution-dir>/.work-spec-migration-<fingerprint-prefix>.json`, publishes the full set under the shared writer mutex and records a matching `.done` marker. If interrupted, preserve all evidence and use `task migration-recover` only after separate recovery authorization, with the identical request and fingerprint.

The TASK-only procedure below remains available for its implemented scope. It does not implement the cross-file reconstruction above and must not be used to bypass that change-set boundary.
