# Programmatic preparation


1. Run `<python-command> "<skill-root>/scripts/work.py" --project-root "<project-root>" task repair-prepare --input-file "<preparation-path>" --user-config-root "<user-config-root>"` with confirmed skill roots. This returns `work-task-repair-prepare/v1` containing `request` and the existing repair validation `preview`. Optionally supply `--output-file "<new-request-path>"` to exclusively create a request file after successful validation; existing files cannot be overwritten. Formal artifacts and transaction state remain unchanged.
2. The input contains exactly `schema: "work-task-repair-prepare-request/v1"`, `stage`, `requirement_id`, the three confirmed `artifacts` paths and nonempty `decisions`, plus optional `edits` or `task`, never both. Omit both for a lossless format candidate from the original parsed TASK, or a complete-stage index binding repair. The program computes original fingerprints and retains every parsed value, unknown field and omission; it does not invent versions, readiness, source bindings, instruction snapshots or semantic content.
3. `edits` is an array of confirmed operations on top-level fields or a TASK row selected by optional `task_id`. Use `{"operation": "add", "field": "summary", "after": "Confirmed missing summary"}` only for absent fields; null is an existing value. Use `{"operation": "replace", "task_id": "TASK-001", "field": "goal", "before": "Old goal", "after": "Confirmed goal"}` for exact replacements, and `{"operation": "remove", "field": "legacy_field", "before": {"retained": "reviewed evidence"}}` for explicitly approved removals. Supply nested objects and arrays as whole field values. Missing or ambiguous TASK IDs, stale old values, duplicate targets and overlapping whole-array/row edits are rejected. Repair decisions must explain the actual changes; successful validation cannot establish user approval or natural-language correctness.
4. Invalid UTF-8, invalid JSON or duplicate keys stop automatic preparation and return diagnostics. Supply an explicit `task` object only after the user resolves the original interpretation; original byte evidence is still preserved by repair validation. Preparation never tries alternate encodings, chooses a duplicate value, infers a missing parent structure or discards unknown content. Complete-stage candidates must pass all existing contract/source checks and execution blockers.
5. Review `data.request` and `data.preview`, including original bytes, TASK/index diffs, diagnostics, affected TASKs and `approved_sha256`. The optional output file contains only the generated request. Otherwise save `data.request`, not the response envelope, for `repair-validate` and approved `repair`. Preparation does not authorize writes or recovery; changed sources, decisions or candidates require a new preview and approval.
